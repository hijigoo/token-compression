# 01-lossless-structure — 의미를 하나도 안 버리는 압축

> **한 줄 요약** — 무손실 압축은 *내용*이 아니라 *표현의 중복*을 먹습니다.
> 그래서 구조화 텍스트에서는 27.5% 줄고, 산문에서는 1% 줄었습니다.

## 어떤 랩인가요

압축이라고 하면 보통 "덜 중요한 것을 버린다"를 떠올리시게 됩니다. 이 랩은
그 반대입니다. **아무것도 버리지 않고** 토큰만 줄입니다.

그런 일이 가능한 이유는, 텍스트에 내용이 아닌데도 토큰을 먹는 부분이
꽤 많기 때문입니다.

| 무엇이 중복인가 | 어디에 있나 |
|---|---|
| 레코드마다 반복되는 **키 이름** | JSON 배열, API 응답 |
| 줄마다 반복되는 **타임스탬프·서비스명** | 로그 |
| 사람이 보라고 넣은 **들여쓰기** | JSON, XML |
| 세로줄을 맞추려고 채운 **정렬 공백** | 마크다운 표, 설정 파일 |

이런 것들은 지워도 의미가 그대로 남습니다. 지우면 안 되는 것과 섞이지만
않는다면요. 이 랩은 그 "섞이지 않았음"을 매번 확인하면서 지웁니다.

## 시작하기

노트북으로 보시는 편이 이해가 빠릅니다. 변환을 하나씩 눈으로 보여드리고,
마지막에 이 랩의 모든 설정을 자동으로 돌려서 비교해 드립니다.

```bash
jupyter lab run.ipynb
```

명령줄로 돌리셔도 됩니다.

```bash
python compress.py configs/structure.yaml            # 구조화 텍스트
python compress.py configs/prose.yaml                # 산문 (대조군)
python compress.py configs/structure-lossy-ws.yaml   # 공백 접기까지
```

준비물은 kit뿐입니다. API 호출도 모델 다운로드도 필요 없어서, 저장소를
받자마자 바로 돌려보실 수 있습니다.

## 결과

`labs/data/sample-structured` 12건 · `sample` 12건
토큰은 **API 실측 기준**입니다(`tokenizer.mode: both`). tiktoken 추정으로는
28.5%로 나오는데, 실측이 1%p 낮은 이유는 메시지 포맷 오버헤드가 압축 후에도
그대로 붙기 때문입니다. 노트북 마지막 절에서 두 값을 나란히 보실 수 있습니다.

| 조건 | 입력 | 절감 | 최저 보존율 | 변환 적용 | 검증됨 |
|---|---|---|---|---|---|
| `structure` | 구조화 12건 | **27.5%** | 100% | 12번 | 12번 (전부) |
| `prose` | 산문 12건 | **1.0%** | 100% | 1번 | 1번 |
| `structure-lossy-ws` | 구조화 12건 | 28.1% | 100% | 14번 | 12번 · **2번 못 함** |

### 무엇을 어떻게 검증했나

"12번 검증"이 무엇을 확인한 것인지 랩이 풀어서 보여줍니다.

```
변환 12번 적용 · 그중 12번 검증
  json_to_table      2회 · 파싱해서 값끼리 비교
  json_compact       2회 · 파싱해서 값끼리 비교
  log_dedup          2회 · 되돌려서 원본과 글자 비교
  kv_compact         2회 · 파싱해서 값끼리 비교
  md_table_compact   2회 · 파싱해서 값끼리 비교
  xml_compact        2회 · 파싱해서 값끼리 비교
```

**`적용`과 `검증`이 같아야** 그 조건 전체를 무손실이라 부를 수 있습니다.
`structure-lossy-ws`에서는 `ws_collapse`가 2회 쓰이는데 확인할 방법이 없어서
14번 중 12번만 검증됩니다.

### 여기서 눈여겨보실 것 세 가지

**1. 같은 알고리즘인데 27.5% 대 1.0%입니다.** 코드는 한 글자도 안 바뀌었고
입력만 다릅니다. 산문 12건 중 11건은 적용할 변환이 아예 없었습니다.
무손실로 얻을 게 있는지는 **입력이 정합니다.**

**2. 공백까지 접어도 0.7%p밖에 더 못 얻습니다.** 그런데 그 대가로 무손실
보장이 사라집니다(원래 공백이 몇 칸이었는지 복원 불가). 0.6%p를 위해
"아무것도 안 잃었다"는 말을 포기하는 건 대개 손해입니다.

**3. 유형마다 이득이 다릅니다.**

| 유형 | 절감 | 왜 |
|---|---|---|
| `json-array` | 43.5% | 레코드가 많을수록 키 반복이 커집니다 |
| `json-nested` | 40.3% | 들여쓰기 4칸이 통째로 사라집니다 |
| `kv-space` | 39.0% | 콜론을 맞추려고 채운 공백이 전부 장식입니다 |
| `md-table` | 31.0% | 정렬 패딩과 구분선(`\|---\|`)이 사라집니다 |
| `log-repeat` | 16.0% | 접두사는 길지만 줄 수가 적으면 이득도 적습니다 |
| `xml` | 12.4% | 태그 이름 자체는 못 줄입니다 |

`json-array`가 압도적인 이유는 이득이 **레코드 수에 비례**하기 때문입니다.
4건짜리 배열에서 37%면, 400건짜리에서는 더 큽니다. 반대로 로그는 줄이 늘어도
접두사 비율이 그대로라 절감률이 수렴합니다.

## "무손실"을 말로만 하지 않으려고 했습니다

이 랩에서 정말 중요한 부분은 압축이 아니라 **검증**입니다. 줄었다는 것은
숫자로 바로 보이지만, 아무것도 잃지 않았다는 것은 증명해야 하기 때문입니다.

그래서 모든 변환이 자기를 검증하는 방법을 함께 들고 오도록 만들었습니다.

| 방법 | 어떻게 | 쓰는 변환 |
|---|---|---|
| `restore` | 되돌려서 원본과 **글자 단위**로 비교 | `log_dedup` |
| `canon` | 양쪽을 정규형으로 바꿔 비교 | `json_*`, `xml_*`, `md_table_*`, `kv_*` |
| (없음) | 검증 불가 → **손실로 분류** | `ws_collapse` |

정규형 비교가 필요한 이유는, 들여쓰기를 지우면 되돌릴 수는 없지만 **잃은
정보는 없기** 때문입니다. JSON의 공백은 내용이 아니므로 파싱한 객체가 같으면
같습니다.

검증이 하나라도 실패하면 **exit 1**입니다. 실제로 잡는지 확인했습니다.

| 심어둔 고장 | 결과 |
|---|---|
| JSON 값 하나를 몰래 삭제 | `bad_drop 정규형이 다릅니다` ✗ |
| 접두사를 틀리게 복원 | `bad_prefix 복원 결과가 원본과 다릅니다` ✗ |
| XML 속성 `port` 삭제 | `bad_xml 정규형이 다릅니다` ✗ |

> **왜 이런 확인을 따로 했는지 말씀드리면** — 예전에 push 훅이 아무것도
> 검사하지 않으면서 통과만 하던 적이 있었습니다. "동작하는 것처럼 보이지만
> 사실 아무 일도 안 하는" 검사는 없느니만 못합니다.
>
> 검증 코드를 손보셨다면, 일부러 고장 낸 입력을 한 번 넣어보시길 권합니다.
> 잡히는 것을 직접 보기 전까지는 믿지 않으시는 편이 안전합니다.

## 변환 목록

| 이름 | 하는 일 | 조건 |
|---|---|---|
| `json_to_table` | 키가 같은 레코드 배열 → 헤더 1줄 + 값 행 | flat·키 동일·2건 이상 |
| `json_compact` | 들여쓰기·구분자 공백 제거 | 파싱되는 JSON |
| `log_dedup` | 줄 공통 접두사를 헤더로 | 3줄 이상·접두사 8자 이상 |
| `xml_compact` | 태그 사이 공백 제거 | 텍스트 노드 없음 |
| `md_table_compact` | 정렬 패딩·구분선 제거 | 열 수 일정 |
| `kv_compact` | `키 : 값`의 정렬 공백 제거 | 3줄 이상 |
| `ws_collapse` | 공백 접기 | **검증 불가 — 기본 파이프라인 제외** |

각 변환은 자기가 다룰 수 없는 입력을 만나면 조용히 건너뜁니다. JSON 변환기에
산문을 넣으시면 아무 일도 일어나지 않는데, 그게 정상 동작입니다. 그래서
파이프라인에 변환을 여러 개 넣어두셔도 안전합니다.

### 순서가 결과를 바꿉니다

```yaml
pipeline:
  - json_to_table     # 성공하면 json_compact 는 건너뜁니다
  - json_compact
  - log_dedup
  - xml_compact
  - md_table_compact
  - kv_compact
```

`json_to_table`이 `json_compact`보다 많이 줄이므로 먼저 시도합니다. 성공하면
같은 입력을 노리는 뒤쪽 변환은 `EXCLUSIVE` 규칙으로 건너뜁니다 — 같은 대상을
두 번 바꾸면 검증이 꼬이기 때문입니다.
