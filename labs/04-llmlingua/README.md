# 04-llmlingua — 작은 모델이 토큰을 골라 버립니다

> **한 줄 요약** — 세 변형 중 **LLMLingua-2만 쓸 만했습니다.** 그리고 같은
> 설정에서 **한국어가 영어보다 먼저 무너집니다.**

## 앞선 랩들과 무엇이 다른가요

| 랩 | 누가 판단하나 | 언어 영향 |
|---|---|---|
| [`01`](../01-lossless-structure/) 무손실 | 규칙 | 없음 |
| [`02`](../02-handle-ref/) 참조핸들 | 겹침 점수 | 적음 |
| [`03`](../03-summarize-llm/) 요약 | **큰 모델**이 다시 씁니다 | 적음 |
| **`04`** 프루닝 | **작은 모델**이 토큰마다 판정합니다 | **큽니다** |

중요도를 매기는 모델이 작기 때문에, 그 모델이 약한 언어에서는 성능이
떨어집니다. 그래서 이 랩만 **한·영 이중언어 코퍼스**를 씁니다.

## 세 형제

같은 `PromptCompressor` 클래스에 파라미터만 다릅니다. 그래서 폴더를 나누지
않고 설정으로 가릅니다.

| 변형 | 무엇이 다른가 | 필요한 것 |
|---|---|---|
| `v1` LLMLingua | 토큰별 정보량으로 프루닝 | 인과 LM |
| `long` LongLLMLingua | **질문**을 주고 문단별 중요도를 함께 봄 | 인과 LM + 질문 |
| `v2` LLMLingua-2 | 분류 모델이 토큰을 남길지 판정 | 전용 인코더 |

## 결과 — `sample-bilingual` 12건 (한·영 6쌍)

### 표 읽는 법

**보존율**은 답에 꼭 필요한 문자열(`must_include`)이 압축 후에도 남은
비율입니다.

```
질문        3월 결제 총액과 환불액은?
필요한 것    ["32,450,000", "1,280,500"]   ← 2개

2개 다 남음 → 100%      1개만 남음 → 50%
```

아래 표의 **`전체` · `한국어` · `영어`는 전부 같은 보존율**입니다. 전체는
12건 평균이고, 나머지는 그중 해당 언어만 골라 낸 평균입니다.

> 지금은 한·영이 6건씩 같아서 전체가 두 언어의 가운데값과 일치합니다.
> **건수가 달라지면 많은 쪽으로 기웁니다.** 한국어 서비스에 쓰실 거라면
> 전체가 아니라 **한국어 열**을 기준으로 보세요.

### ⓪ 한 케이스로 먼저 — 같은 내용, 다른 언어

같은 사실을 담은 한·영 쌍에 셋을 각각 걸었습니다(`rate=0.5`).

| 케이스 | 변형 | 토큰 | 절감 | 보존율 | 남은 정답 문자열 |
|---|---|---|---|---|---|
| `ko-01` | `v1` | 116 → 116 | 0.0% | 100% | 32,450,000 · 1,280,500 |
| `ko-01` | `long` | 116 → 61 | 47.4% | 50% | 1,280,500 |
| `ko-01` | `v2` | 116 → 74 | 36.2% | 50% | 1,280,500 |
| `en-01` | `v1` | 94 → 93 | 1.1% | 100% | 32,450,000 · 1,280,500 |
| `en-01` | `long` | 94 → 41 | 56.4% | **0%** | **(전부 사라짐)** |
| `en-01` | `v2` | 94 → 59 | 37.2% | **100%** | 32,450,000 · 1,280,500 |

**`v1`의 보존율 100%는 잘해서가 아닙니다** — 아무것도 안 버려서(절감 0~1%)
나온 값입니다. **`v2`만 언어에 따라 갈립니다** — 영어는 100%인데 한국어에서만
`32,450,000`이 사라졌습니다.

### ① 변형 비교 (`rate=0.5`)

| 설정 | 모델 | 절감 | 보존율 전체(12건) | 한국어(6건) | 영어(6건) |
|---|---|---|---|---|---|
| `v1` | 0.5B | 16.4% | 70.8% | 66.7% | 75.0% |
| `long` | 0.5B | 48.9% | **41.7%** | 58.3% | **25.0%** |
| `long-large` | 1.5B | 49.4% | **41.7%** | 50.0% | 33.3% |
| `v2` | 700MB | 46.3% | 70.8% | 58.3% | 83.3% |
| **`v2-large`** | **2.2GB** | **48.1%** | **79.2%** | **66.7%** | **91.7%** |

`v2`의 전체 70.8%만 보면 무난해 보이지만, **한국어만 보면 58.3%**입니다.

### 큰 모델을 쓰면 나아집니다 — `v2`만

```bash
python compress.py configs/v2-large.yaml
python compress.py configs/v2.yaml --model large    # 또는 플래그로
```

`v2`는 큰 모델에서 **더 줄이면서 더 지켰습니다.**

| | 절감 | 보존율 | 한국어 |
|---|---|---|---|
| `small` (700MB) | 46.3% | 70.8% | 58.3% |
| **`large` (2.2GB)** | **48.1%** | **79.2%** | **66.7%** |

숫자 서식도 달라집니다. 작은 모델은 벌려 놓는데 큰 모델은 그대로 둡니다.

```
small   … 32, 450, 000원입니다 … 3. 9 % 에
large   … 32,450,000원입니다 … 3.9%에
```

**`long`은 큰 모델로도 안 고쳐졌습니다.** 1.5B(3배)로 돌려도 보존율이
41.7% 그대로였고, `use_sentence_level_filter`도 시험했지만 같았습니다.
숫자 중간이 잘리는 것은 **토큰 단위로 버리는 방식 자체의 특성**으로 보입니다.

**`v2`가 유일하게 쓸 만합니다.** `long`은 가장 많이 줄였지만 보존율이 절반도
안 됩니다. 질문까지 주는데도 결과가 가장 나쁜 이유는 아래에서 설명합니다.

### ② 압축률 스윕 (`v2`) — 한국어가 먼저 무너집니다

| `rate` | 절감 | 전체(12건) | **한국어(6건)** | **영어(6건)** |
|---|---|---|---|---|
| 0.9 | 8.4% | 95.8% | 100% | 91.7% |
| 0.7 | 27.8% | 79.2% | **66.7%** | **91.7%** |
| 0.5 | 46.6% | 70.8% | 58.3% | 83.3% |
| 0.3 | 64.8% | 58.3% | 58.3% | 58.3% |

`rate=0.7`을 보세요. 영어는 아직 91.7%인데 **한국어는 이미 66.7%로 떨어졌습니다.**
같은 설정, 같은 내용인데 언어가 다릅니다.

> `rate`는 **남길 비율**입니다. 공식 문서에 `ratio`로 적힌 곳이 있는데
> 실제 인자명은 `rate`입니다. `target_token`을 함께 주면 `rate`를 덮어씁니다.

### ③ 한국어는 애초에 토큰을 더 씁니다

| | 문자 | 토큰 | 문자당 |
|---|---|---|---|
| 한국어 | 1,702자 | 918 | 0.54 |
| 영어 | 3,272자 | 958 | 0.29 |

**같은 내용에 한국어가 문자당 1.8배**를 씁니다(`o200k_base` 기준). 압축이
더 절실한 쪽인데 압축 품질은 더 나쁩니다.

## 레이턴시 트레이드오프 — 압축은 공짜가 아닙니다

여기까지는 **얼마나 줄었나**만 봤습니다. 그런데 압축 자체도 시간을 씁니다.
작은 모델을 한 번 더 돌리는 일이니까요. 끝에서 끝까지 재봤습니다.

`longdoc`·`structured` 6건 · 모델 로딩은 미리 끝내고 측정 · 중앙값

| 조건 | 토큰 | 절감 | 보존 한국어 | 보존 영어 | 압축 소요 | 응답 소요 | **합계** |
|---|---|---|---|---|---|---|---|
| 압축 없음 | 1,191 → 1,191 | 0.0% | 100% | 100% | 0ms | 2.57s | **2.57s** |
| `v2 small` | 1,191 → 614 | 48.4% | 66.7% | 66.7% | 90ms | 2.53s | **2.62s** |
| `v2 large` | 1,191 → 599 | 49.7% | 66.7% | 83.3% | 236ms | 3.57s | **3.81s** |

**토큰은 절반으로 줄었는데 합계는 늘었습니다.**

이 규모(약 1,200토큰)에서는 응답 시간이 입력 길이가 아니라 **출력 생성과
왕복 네트워크**에 좌우됩니다. 입력을 절반으로 줄여도 응답은 거의 그대로인데
압축 시간만 얹히는 셈입니다.

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 비용 | 입력 토큰 **약 절반** | — |
| 속도 | — | 압축 시간만큼 **느려짐** |
| 정확도 | — | 보존율이 100% 아래로 |

**이 규모에서 압축은 비용 최적화이지 속도 최적화가 아닙니다.**

### 속도에도 도움이 되는 때

입력이 충분히 커서 **프리필이 병목**이 될 때입니다. 수만 토큰을 넣으면
입력을 읽는 시간 자체가 길어지고, 그때는 절반으로 줄인 효과가 압축 비용을
넘어섭니다.

```
압축으로 아끼는 시간 ≈ (줄인 토큰 수) × (토큰당 프리필 시간)
압축에 쓰는 시간     ≈ 90~240ms        (v2 · 이 코퍼스 실측)

앞이 뒤보다 커야 속도로도 이득입니다.
```

`small`이 압축은 2.6배 빠릅니다(90ms vs 236ms). 속도가 급하면 `small`,
정확도가 급하면 `large`입니다 — 다만 **이 규모에서는 둘 다 속도 이득이
없습니다.**

## 왜 `v1`/`long`이 나쁜가 — 정직하게

**모델 크기 때문입니다.** 논문은 Llama-2-7B를 썼는데 이 랩은 `Qwen2.5-0.5B`를
씁니다. 13GB를 받게 하고 싶지 않았습니다.

작은 모델로 토큰 단위 프루닝을 하면 이렇게 됩니다.

```
원문        the total amount charged was 32,450,000 KRW. Of that, 1,280,500 …
long r=0.5  the total amount charged was 32.  Of0 was, Com to February the7
long r=0.9  the total amount charged was 32,450,00RW.  Of that, 1,28
                                         ↑ 숫자 중간이 잘립니다
```

`rate=0.9`(10%만 버림)에서도 `32,450,000 KRW`가 `32,450,00RW`가 됩니다.
**토큰 단위로 자르기 때문에 숫자와 식별자가 조각납니다.**

`v2`가 안전한 이유는 분류 모델이 단어에 가까운 단위로 판정해서 숫자를 통째로
남기기 때문입니다.

> **처음엔 모델 크기 탓이라고 봤는데, 재보니 아니었습니다.** 3배 큰
> 1.5B로 돌려도 보존율이 41.7% 그대로였고 `use_sentence_level_filter`도
> 효과가 없었습니다. 토큰 단위로 버리는 방식에서는 숫자가 여러 토큰으로
> 쪼개져 있어 하나만 빠져도 깨지는 것으로 보입니다.
>
> 7B(`paper`)는 안 해봤으니 거기서 달라질 여지는 남아 있습니다.

## `v2`도 원문을 그대로 두지 않습니다

`rate=1.0`은 아무것도 버리지 않는다는 뜻인데, 돌려보면 **토큰이 늘어납니다.**

```bash
python compress.py configs/v2-noop.yaml
# → 절감 -3.3% · 보존율 100%
```

```
전  총 결제 건수는 1,284건이며 결제 총액은 32,450,000원입니다 … 3.9%에
후  총 결제 건수는 1, 284건이며 결제 총액은 32, 450, 000원입니다 … 3. 9 % 에
```

토큰에서 텍스트를 다시 만들기 때문에 쉼표와 기호 주변이 벌어집니다.
**숫자가 많은 짧은 글에서는 압축이 오히려 손해**입니다.

정보는 남아 있어서 보존율은 100%입니다. `kit`의 보존율 계산이 쉼표·공백을
지우고 비교하기 때문입니다. 그래서 이 랩의 자가 점검은 토큰이 아니라
**보존율**을 봅니다.

## 조용히 무시되는 인자를 막았습니다

이 랩에서 가장 조심할 부분입니다. `use_llmlingua2=True`인 압축기에
`question`이나 `rank_method`를 넘기면 **에러 없이 무시됩니다.**
LongLLMLingua 설정을 v2에 잘못 붙여도 그냥 돌아가고 결과만 v2 그대로입니다.

숫자가 안 바뀌는 이유를 찾느라 시간을 버리기 쉬워서, 어댑터가 거부합니다.

```
variant=v2 이 쓰지 않는 인자입니다: ['question', 'rank_method']
  LongLLMLingua 전용 인자로 보입니다. v2 는 질문을 쓰지 않습니다 —
  variant 를 long 으로 바꾸시거나 이 인자를 빼주세요.
```

케이스를 다 돌린 뒤가 아니라 **설정을 읽자마자** 확인합니다.

## 설정

| 파라미터 | 뜻 | 기본 |
|---|---|---|
| `variant` | `v1` / `long` / `v2` | `v2` |
| `model_name` | `small` / `large` / `paper` 또는 HuggingFace 경로 | `small` |
| `rate` | **남길** 비율 | `0.5` |
| `force_reserve_digit` | 숫자를 지키려 시도합니다 | `false` |
| `force_tokens` | 항상 남길 토큰 | `[]` |
| `target_token` | 목표 토큰 수. **`rate`를 덮어씁니다** | `-1` |

`long`은 `rank_method`와 `condition_compare`를 어댑터가 기본으로 켭니다.
질문 기반 재순위가 이 변형의 핵심이기 때문입니다.

## 고를 수 있는 모델

```yaml
params:
  model_name: large      # small | large | paper | HuggingFace 경로
```

```bash
python compress.py configs/v2.yaml --model large
python compress.py configs/v1.yaml --model Qwen/Qwen2.5-3B
```

| 변형 | `small` (기본) | `large` | `paper` |
|---|---|---|---|
| `v1`·`long` | Qwen2.5-0.5B (1GB) | Qwen2.5-1.5B (3GB) | Llama-2-7b (13GB) |
| `v2` | bert-base-multilingual (700MB) | **xlm-roberta-large (2.2GB)** | — |

기본이 `small`인 이유는 저장소를 받자마자 돌려보실 수 있어야 해서입니다.
**실제로 쓰실 거라면 `v2` + `large`로 한 번 재보시고 판단하세요.**

## 알아두시면 좋은 한계

- **기본이 작은 모델입니다.** `v2`는 `large`로 바꾸면 확실히 나아지지만,
  `v1`/`long`은 1.5B로 올려도 그대로였습니다. 7B(`paper`)는 안 해봤습니다.
- 코퍼스가 12건으로 작습니다. 경향을 보는 용도이지 벤치마크가 아닙니다.
- `v2`의 다국어 모델은 MeetingBank(회의록)로 학습됐습니다. 문서 성격이
  다르면 결과가 달라질 수 있습니다.
- 보존율은 문자열 검사라 하한입니다. 실제 정답률은
  [`compare/qa_eval.py`](../../compare/)로 재실 수 있습니다.

## 언제 쓰시면 좋을까요

| 상황 | 판단 |
|---|---|
| 영어 장문, 중간 압축(rate 0.7 이상) | **적합** — `v2` |
| 한국어 | **주의** — 같은 rate에서 영어보다 먼저 깨집니다 |
| 숫자·식별자가 답인 문서 | **부적합** — 서식이 깨집니다 |
| 짧은 글 | **부적합** — 오히려 늘어날 수 있습니다 |
| 표·JSON | **부적합** — [`01`](../01-lossless-structure/)이 무손실로 처리합니다 |
