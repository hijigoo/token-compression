# 02-handle-ref — 버리지 않고 밖에 둡니다

> **한 줄 요약** — 같은 비용(k=1)으로 보존율이 **100%도 되고 43.8%도 됩니다.**
> 차이는 압축 알고리즘이 아니라 **무엇을 펼칠지 고르는 방법**입니다.

## 어떤 랩인가요

무손실([`01`](../01-lossless-structure/))은 표현의 중복까지가 천장입니다.
더 줄이시려면 무언가를 빼야 하는데, 빼는 방법이 두 가지 있습니다.

| | 정보는 | 되돌리기 |
|---|---|---|
| [`03-summarize-llm`](../03-summarize-llm/) | 요약하며 **없앱니다** | 불가 |
| **`02-handle-ref`** | 밖에 두고 **핸들만** 남깁니다 | 꺼내면 원문 그대로 |

핸들 방식은 아무것도 잃지 않습니다. 원문이 저장소에 그대로 남아 있으니까요.
대신 **꺼낼 것을 골라야** 하고, 잘못 고르면 답을 하지 못합니다.

그래서 이 랩에서 일어나는 실패는 전부 라우팅 실패입니다. 압축 알고리즘이
아니라 고르는 방법을 들여다보시게 됩니다.

```
원문                          컨텍스트에 들어가는 것
┌────────────┐               ┌──────────────────────────┐
│ ■ 개요     │  ──저장──▶    │ [[b1]] 개요: 본 문서는…   │  ← 다이제스트
│ ■ 환불규정 │               │ [[b2]] 환불규정           │
│ ■ 적용범위 │               │ 환불은 결제일로부터 30일… │  ← 펼침
│ …          │               │ [[b3]] 적용범위: 유료…    │
└────────────┘               └──────────────────────────┘
```

## 시작하기

노트북으로 보시는 편이 이해가 빠릅니다. 블록이 어떻게 쪼개지고 무엇이
펼쳐지는지 눈으로 보여드린 뒤, 이 랩의 모든 설정을 자동으로 돌려 비교해
드립니다.

```bash
jupyter lab run.ipynb
```

명령줄로 돌리셔도 됩니다. `--sweep`을 쓰시면 `expand_k`를 여러 값으로
연달아 돌려서 곡선을 볼 수 있습니다.

```bash
python compress.py configs/k1.yaml                      # 기본 조건
python compress.py configs/k1.yaml --sweep 0,1,2,3,all  # 곡선 보기
python compress.py configs/k1-no-router.yaml --sweep 1,2,3,4,all
```

준비물은 kit뿐입니다. API도 모델 다운로드도 필요 없습니다.

## 결과

`labs/data/sample-long` 8건(각 7개 절, 정답은 한 절에만) · 원문 3,749토큰

### ① 라우팅이 있을 때와 없을 때 — 이 랩에서 가장 중요한 표입니다

같은 `k`, 같은 토큰 비용인데 결과가 갈립니다.

| 펼침 | 라우팅 `bigram` |  | 라우팅 없음 `first` |  |
|---|---|---|---|---|
| | 절감 | 최저 보존율 | 절감 | 최저 보존율 |
| 1 | 50.9% | **100%** | 49.7% | **0%** |
| 2 | 38.9% | **100%** | 38.3% | **0%** |
| 3 | 28.4% | **100%** | 28.0% | **0%** |
| 4 | — | — | 17.6% | **0%** |
| all | -3.2% | 100% | -3.2% | 100% |

`first`는 문서 앞에서부터 k개를 남기는, 가장 흔한 절단 방식입니다. 4개를
펼쳐도(=절감을 17.6%까지 포기해도) 최저 보존율이 **0%**입니다. 정답이 뒤쪽
절에 있는 문서는 아무리 앞을 남겨도 못 찾기 때문입니다.

> **토큰을 더 쓴다고 정확도가 오르지는 않습니다.** 어디를 남기느냐가
> 정합니다.
>
> 코퍼스를 만들 때 정답 절의 위치를 문서마다 흩어 놓은 이유이기도 합니다.
> 정답이 항상 앞에 있으면 앞에서 자르기만으로도 통과해 버려서, 라우터가
> 제 몫을 하는지 평가할 수가 없습니다.

### ② 다이제스트 길이 — 오버헤드는 생각보다 큽니다

| 다이제스트 | 절감 (k=1) | 최저 보존율 |
|---|---|---|
| 본문 24자 미리보기 | 50.9% | 100% |
| **제목만** (`digest_chars: 0`) | **69.1%** | 100% |

미리보기 24자를 지우는 것만으로 절감이 **18%p** 뜁니다. 절 제목이 이미
충분히 설명적이면 미리보기는 순수 낭비입니다. 제목이 `섹션1`, `기타` 같은
문서라면 반대가 됩니다.

### ③ 짧은 글에는 권해드리지 않습니다

`labs/data/sample`(평균 150자) 산문에 같은 기법:

| 펼침 | 절감 | 최저 보존율 |
|---|---|---|
| 1 | **1.5%** | 33.3% |
| all | **-9.5%** | 100% |

`all`에서 절감이 마이너스입니다. 핸들 표시(`[[b1]]`)와 색인 헤더가 원문보다
커져버렸기 때문입니다. **참조 핸들은 문서가 충분히 길고 블록 경계가 뚜렷할
때만 이깁니다.**

## 절감률을 그대로 믿으시면 안 되는 이유

여기 절감률은 **꺼내기 전** 기준입니다. 모델이 `[[b2]]`를 요청하면 그 블록이
컨텍스트로 들어오고, 절감분은 그만큼 되돌아옵니다.

모델이 `[[b2]]`를 요청하면 호출이 한 번 더 붙고, **다이제스트를 두 번
보내므로 입력 토큰도 두 번 과금됩니다.**

문서 1건 기준(이 코퍼스 평균 469토큰):

| 방식 | 호출 | 입력 토큰 합 | 절감 |
|---|---|---|---|
| 원문을 통째로 | 1회 | 469 | 기준 |
| 핸들 — 위 표가 보여준 것 | 1회분만 | 230 | **50.9%** |
| 핸들 — 실제 (왕복 포함) | **2회** | 405 | **13.6%** |

**50.9%가 13.6%로 줄어듭니다.** 지연도 2배입니다.

이기는 조건은 셋입니다.

| 조건 | 왜 |
|---|---|
| 같은 문서에 질문을 **여러 번** | 색인 만드는 비용이 나눠집니다 |
| 문서가 **훨씬 클 때** | 다이제스트 비중이 작아집니다 |
| **프롬프트 캐시**가 먹을 때 | 매번 같은 다이제스트라 적중률이 높습니다 |

질문 수에 따른 실제 절감:

| 질문 수 | 1 | 2 | 3 | 5 | 10 |
|---|---|---|---|---|---|
| 절감 | 13.6% | 32.3% | 38.5% | 43.5% | 47.2% |

**한 번 묻고 끝이면 원문을 통째로 주는 편이 낫습니다.**

## 자가 점검

`expand_k=all`은 **보존율 100%**가 나와야 합니다. 전부 펼쳤는데도 정답
문자열이 없다면 블록으로 쪼개는 과정에서 글자를 흘린 것이고, 그건 라우팅
문제가 아니라 버그입니다.

스윕에 `all`이 들어 있으면 자동으로 검사하고, 어긋나면 **exit 1**로 알려
드립니다.

`정답절적중`은 코퍼스가 정답 절을 알려줄 때만 셉니다(`meta.answer_section`).

> 처음 구현에서는 이 값이 `k=0`인데도 100%로 나왔습니다. "제목이 출력에
> 들어 있나"로 셌는데, 펼치지 않은 블록의 다이제스트에도 제목이 남아 있어서
> 그랬습니다. 지금은 **실제로 펼친 블록**의 제목만 셉니다.
>
> 진단 지표가 틀리면 실패 원인을 정반대로 읽게 되니, 이런 값은 한 번씩
> 의심해 보시는 편이 좋습니다.

## 설정

| 파라미터 | 뜻 | 기본 |
|---|---|---|
| `expand_k` | 펼칠 블록 수. `all`이면 전부 | `1` |
| `route` | `bigram`(질문 기반) / `first`(앞에서) / `last`(뒤에서) | `bigram` |
| `split` | `auto` / `section` / `paragraph` / `sentence` | `auto` |
| `digest_chars` | 안 펼친 블록의 미리보기 길이. `0`이면 제목만 | `24` |
| `per_block` | `sentence` 분할일 때 블록당 문장 수 | `2` |

`auto`는 `■ 제목` 형태의 절 표시를 먼저 찾고, 없으면 문단, 그것도 없으면
문장 단위로 내려갑니다. 사람이 이미 나눠 둔 경계가 기계가 다시 나눈 것보다
대체로 낫기 때문입니다.

### 라우터를 왜 이렇게 만들었나요

한국어는 띄어쓰기로 자르면 조사 때문에 잘 안 맞습니다(`수수료율은` vs
`수수료`). 그래서 **글자 2-gram 겹침**을 씁니다.

임베딩을 쓰면 더 나은 결과가 나오겠지만, 그러면 이 랩이 검색 랩이 되어
버립니다. 여기서 보고 싶은 것은 검색 품질이 아니라 **라우팅 품질이 보존율을
어떻게 흔드는가**이기 때문에, 라우터는 일부러 단순하게 두었습니다.

## 알아두시면 좋은 한계

- **모델이 실제로 핸들을 부르는지는 여기서 재지 않습니다.** 도구 호출 루프는
  [`scripts/explore/04_reference_handle.ipynb`](../../scripts/explore/04_reference_handle.ipynb)에
  있고, 종단 성능은 `agentic-eval` 축에서 다룰 질문입니다.
- 라우터가 정답 블록을 **알고 고르는 것이 아니라** 질문과의 표면적 겹침으로
  고릅니다. 질문에 나오지 않는 단어로 답해야 하는 문서에서는 무너집니다.
- 정답이 두 절에 걸쳐 있으면 `k=1`로는 잡지 못합니다. 그럴 때는 `k`를 늘리시거나
  분할 방식을 바꿔보시면 됩니다.
