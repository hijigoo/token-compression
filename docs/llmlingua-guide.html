1 왜 프롬프트를 압축하나

LLM을 실제로 쓰다 보면 부딪히는 3가지 벽이 있습니다.

💰 비용

API는 토큰당 과금. 긴 RAG 컨텍스트를 매번 보내면 비용이 선형으로 증가합니다.

📏 길이 제한

컨텍스트 윈도우를 넘으면 아예 요청이 실패합니다.

🕳 Lost in the Middle

컨텍스트가 길면 중간에 있는 정보를 놓칩니다. 길다고 좋은 게 아닙니다.

핵심 통찰 — 자연어에는 잉여(redundancy)가 많다

LLMLingua의 출발점은 정보이론입니다. 사람이 쓴 문장에는 모델이 이미 예측할 수 있는 토큰이 잔뜩 들어있습니다. 예측 가능한 토큰은 정보량이 적으므로 지워도 손실이 적습니다.

Sam bought a dozen boxes , each with 30 highlighter pens inside , for $10 each box
■ 유지 — 예측 불가 = 정보량 높음 ■ 제거 — 예측 가능 = 잉여
놀라운 점. 압축된 프롬프트는 사람이 읽으면 깨진 문장처럼 보이지만, LLM은 여전히 의미를 복원해 정답을 냅니다. 실제로 GPT-4는 압축 프롬프트에서 원래 정보를 거의 전부 복구할 수 있습니다.

실제 압축 예시 (공식 README)

# 원본 2,365 토큰 → 압축 211 토큰 (11.2x)
{
  'compressed_prompt': 'Question: Sam bought a dozen boxes, each with 30 highlighter
    pens inside, for $10 each box. He reanged five of boxes into packages of
    sixlters each and sold them $3 per...',
  'origin_tokens':     2365,
  'compressed_tokens': 211,
  'ratio':  '11.2x',
  'saving': ', Saving $0.1 in GPT-4.'
}

reanged, sixlters 처럼 단어가 깨져 보이죠. 토큰 단위로 지우기 때문입니다. 그래도 모델은 문제를 풉니다.

2 기본 동작 원리 — 3단계 파이프라인

LLMLingua는 작은 모델(GPT2-small, LLaMA-7B 등)로 각 토큰의 중요도를 재고, 덜 중요한 것부터 지웁니다. 큰 모델은 전혀 건드리지 않습니다.

1

Budget Controller — 예산 배분 거친 단계

프롬프트를 instruction / context / question으로 나누고 부분별 압축 강도를 정합니다. 핵심은 민감도가 다르다는 것입니다. 

# 압축 민감도
instruction  높음  ← 지시문이 망가지면 치명적. 거의 안 건드림
question     높음  ← 질문이 망가지면 답이 산으로 감
context      낮음  ← 문서·예시는 과감히 압축 가능

이 단계에서 문서(context) 단위로 통째 버리기도 수행합니다 (use_context_level_filter).

2

Iterative Token-level Compression — 반복 토큰 압축 핵심

남은 텍스트를 iterative_size(기본 200) 토큰씩 끊어가며 작은 모델로 perplexity(당황도)를 계산합니다. 

# 개념
for segment in chunks(text, size=200):
    ppl = small_model.perplexity(segment)   # 토큰별 예측 난이도
    keep = ppl > threshold                  # 예측 어려운 것 = 정보량 큼 → 유지
    text = text[keep]
왜 "반복(iterative)"인가? 토큰을 지우면 남은 토큰의 확률 분포가 바뀝니다. 한 번에 전부 계산하면 이 상호작용을 놓치므로, 조각씩 순차 처리하며 앞서 압축된 결과를 반영합니다.
3

Distribution Alignment — 분포 정렬

작은 모델과 큰 모델(GPT-4 등)은 토큰 확률 분포가 다릅니다. 작은 모델이 "쉽다"고 본 토큰이 큰 모델에겐 중요할 수 있죠. 이 간극을 줄이기 위해 작은 모델을 큰 모델의 출력에 맞춰 정렬합니다.

정리

원본 프롬프트
   ↓  ① Budget Controller     — 부분별 예산 + 문서 단위 필터
   ↓  ② Iterative Token       — 200토큰씩 perplexity 기반 삭제
   ↓  ③ Distribution Align    — 작은 모델 ↔ 큰 모델 간극 보정
압축 프롬프트  →  GPT-4 등 대형 모델로 전송
가장 큰 장점 — LLM 재학습이 전혀 필요 없습니다. 압축은 순수히 전처리입니다. 기존 파이프라인 앞에 끼워 넣기만 하면 됩니다.

3 예시로 따라가는 전체 흐름

사내 규정 챗봇 시나리오입니다. 실제 입력을 넣고 3단계를 거치며 무엇이 어떻게 지워지는지 끝까지 따라가 봅니다.

📥 입력 — 압축 전 원본 약 1,000 토큰
INSTRUCTION
아래 사내 규정 문서를 참고하여 질문에 정확히 답하세요. 근거가 없으면 모른다고 답하세요.
CONTEXT — 문서 1 (연차 규정)
제12조(연차휴가의 이월) 회사는 근로기준법에 따라 연차유급휴가를 부여한다. 미사용 연차는 다음 해로 최대 5일까지 이월할 수 있으며, 이월된 연차는 이월된 해의 6월 30일까지 사용하여야 한다. 기간 내 미사용 시 소멸된다.
CONTEXT — 문서 2 (출장비 규정)
제31조(출장비) 국내 출장 시 일비는 2만원, 숙박비는 실비로 정산한다. 해외 출장의 경우 지역 등급에 따라 차등 지급하며, 항공권은 이코노미석을 원칙으로 한다.
CONTEXT — 문서 3 (휴가 신청 절차)
제14조(휴가 신청) 연차 사용 희망일 3일 전까지 그룹웨어를 통해 신청하여야 하며, 팀장의 승인을 받아야 한다. 이월 연차도 동일한 절차를 따른다.
QUESTION
연차는 며칠까지 이월되나요?
▼ ▼ ▼
① Budget Controller — 예산 배분 & 문서 선별 1,000 → 약 620 토큰

먼저 부분별 압축 민감도에 따라 예산을 나눕니다.

INSTRUCTION  민감도 높음  → 압축률 0.9  # 거의 손대지 않음
QUESTION     민감도 높음  → 압축률 1.0  # 그대로 보존
CONTEXT      민감도 낮음  → 압축률 0.4  # 여기서 대부분 절감

다음으로 문서 단위 필터링 (use_context_level_filter=True)

각 문서가 질문과 얼마나 관련 있는지 점수를 매기고, 예산에 안 맞는 문서는 통째로 버립니다.

문서 1 · 연차 이월 관련도 0.94 유지
"이월", "연차", "5일" — 질문의 핵심어와 직접 일치
문서 2 · 출장비 관련도 0.06 ✗ 제거
연차와 무관한 내용 → 문서 통째로 삭제
문서 3 · 신청 절차 관련도 0.41 약하게 유지
"이월 연차"가 언급되나 "며칠"에 대한 답은 없음 → 남기되 강하게 압축
이 단계가 가장 효율이 좋습니다. 관련 없는 문서 하나를 통째로 버리는 것이 토큰을 하나씩 지우는 것보다 훨씬 크게 절감됩니다. RAG에서 검색기가 문서를 10개 가져왔다면 실제로 필요한 건 2~3개인 경우가 많습니다.
▼ ▼ ▼
② Iterative Token-level Compression — 토큰 단위 삭제 620 → 약 180 토큰

남은 텍스트를 200 토큰씩 끊어서 작은 모델에 넣고, 각 토큰의 perplexity(예측 난이도)를 잽니다.

왜 "반복(iterative)"인가. "할 수 있으며"를 지우고 나면 그 뒤 문장의 확률 분포가 달라집니다. 전체를 한 번에 계산하면 이 상호작용을 놓치므로, 200토큰 조각을 순서대로 처리하며 앞선 압축 결과를 반영합니다.
▼ ▼ ▼
③ Distribution Alignment — 분포 정렬 토큰 수 변화 없음

판정을 내린 건 작은 모델(LLaMA-7B)인데, 실제로 이 프롬프트를 읽을 모델은 GPT-4입니다. 두 모델은 토큰 확률 분포가 다릅니다. 

# 예: 법률 용어 "소멸된다"
작은 모델   → "흔한 표현이네, 지워도 됨"
GPT-4      → "법적 효력을 결정하는 핵심어"

# 이 간극을 방치하면 중요한 토큰이 잘못 삭제됨

그래서 작은 모델을 큰 모델의 출력 분포에 맞춰 정렬합니다. 토큰 수는 그대로지만 어떤 토큰을 남길지의 판단 품질이 올라갑니다.

▼ ▼ ▼
📤 출력 — 압축 결과 1,000 → 180 토큰 (5.6x) 
아래 사내 규정 참고 질문 답. 근거 없으면 모른다 답.

제12조 연차휴가 이월 근로기준법 연차유급휴가 부여.
미사용 연차 최대 5일 이월, 이월 연차 6월 30일까지 사용.

이 예시를 코드로

from llmlingua import PromptCompressor

llm_lingua = PromptCompressor()

docs = ["제12조(연차휴가의 이월)...",
        "제31조(출장비)...",          # ← ①단계에서 제거될 문서
        "제14조(휴가 신청)..."]

result = llm_lingua.compress_prompt(
    docs,
    instruction="아래 사내 규정 문서를 참고하여 질문에 정확히 답하세요.",
    question="연차는 며칠까지 이월되나요?",
    target_token=180,
    force_reserve_digit=True,     # ★ "5일", "6월 30일" 보호
)

print(result["compressed_prompt"])
print(result["ratio"])        # → '5.6x'
force_reserve_digit=True에 주목하세요. 이 예시에서 "5일"이 사라지면 답을 못 합니다. 숫자가 답인 문서를 다룰 때는 반드시 켜야 하는 옵션입니다.

※ 위 perplexity 수치와 관련도 점수는 원리 설명을 위한 예시값입니다. 실제 값은 사용하는 압축 모델과 문서에 따라 달라집니다.

2 LongLLMLingua — 무엇이 추가됐나

한 문장 요약: "질문을 알고 압축한다." LLMLingua는 질문을 안 보고 지웠지만, LongLLMLingua는 질문에 답하는 데 필요한 것을 남깁니다.

① Question-aware 압축

토큰 중요도를 질문 조건부로 계산합니다. "이 토큰이 질문에 답하는 데 도움이 되는가?" 

# 대비(contrastive) 관점
중요도 = P(토큰 | 질문 있음)
       − P(토큰 | 질문 없음)

파라미터: condition_in_question, condition_compare

② 문서 재정렬 (Reordering)

Lost in the Middle 대응. 관련성 높은 문서를 앞쪽으로 옮깁니다. LLM은 앞·뒤를 잘 보고 중간을 놓치니까요. 

reorder_context="sort"
③ 동적 압축률

모든 문서를 똑같이 압축하지 않습니다. 중요한 문서는 살살, 덜 중요한 건 세게 압축합니다. 

dynamic_context_compression_ratio=0.3
④ 서브시퀀스 복원

압축 때문에 고유명사·숫자가 깨지는 문제를 후처리로 보정합니다. 모델 응답에서 깨진 조각을 원본과 매칭해 되살립니다. 

llm_lingua.recover(...)
랭킹 방식도 선택 가능. 문서 중요도 계산에 longllmlingua(기본), bm25, gzip, sentbert, openai, bge, bge_reranker, cohere, voyageai, jinza 등을 rank_method로 지정할 수 있습니다.
주의 — question이 반드시 필요합니다. rank_method="longllmlingua"인데 question이 비어있으면 코드가 assert로 막습니다. 질문 없이 쓰려면 그냥 LLMLingua나 LLMLingua-2를 쓰세요.

3 LLMLingua-2 — 접근 자체가 다르다

앞의 둘은 perplexity를 계산했습니다. LLMLingua-2는 "이 토큰을 남길까 말까"를 분류(classification)합니다.

1

데이터 증류 (Data Distillation)

GPT-4에게 "의미를 유지하며 압축하라"고 시켜 대량의 (원문 → 압축문) 쌍을 만듭니다. 이게 학습 데이터가 됩니다.

2

토큰 라벨링

원문의 각 단어에 keep / drop 라벨을 붙여 이진 분류 문제로 바꿉니다.

Sam KEEP   bought KEEP   a DROP   dozen KEEP   boxes KEEP
3

인코더 학습 BERT 계열

XLM-RoBERTa-large / mBERT-base를 토큰 분류기로 파인튜닝합니다.

여기가 핵심. BERT는 양방향(bidirectional)이라 문장 전체를 한 번에 보고 단 1회 forward pass로 모든 토큰을 판정합니다. 반복 계산이 필요한 perplexity 방식보다 3~6배 빠른 이유입니다.
4

추론 — 확률 높은 토큰만 유지

probs = encoder(text)              # 각 토큰의 KEEP 확률
keep  = top_k(probs, rate=0.33)     # 상위 33%만 남김

왜 "task-agnostic"이 장점인가

LongLLMLingua — task-aware
  • 질문을 알아야 압축 가능
  • 질문이 바뀌면 다시 압축
  • 캐싱 어려움
  • 대신 그 질문에는 최적
LLMLingua-2 — task-agnostic
  • 질문 없이 압축 가능
  • 한 번 압축해 재사용 ✅
  • 캐싱 쉬움 → 실시간 서비스 적합
  • 처음 보는 도메인에도 견고 (OOD)

제공 모델 2종

모델크기특징
microsoft/llmlingua-2-xlm-roberta-large-meetingbank large 정확도 우선. 다국어(XLM-R). 기본 권장
microsoft/llmlingua-2-bert-base-multilingual-cased-meetingbank base 속도·경량 우선. 다국어 BERT. 리소스 제약 환경

※ 두 모델 모두 MeetingBank 데이터로 학습됐습니다. 자체 도메인 데이터로 재학습하려면 저장소의 experiments/llmlingua2/data_collection · model_training을 참고하세요.

4 어떤 걸 골라야 하나 — 결정 트리

질문(question)이 미리 정해져 있나?
├─ YES → RAG · 문서 QA 인가?
│         ├─ YES → LongLLMLingua   # 질문 인식 + 재정렬
│         └─ NO  → LLMLingua       # CoT · ICL
└─ NO  → 속도·비용이 중요한가?
          ├─ YES → LLMLingua-2     # 3~6배 빠름, 캐싱 가능
          └─ NO  → LLMLingua
LLMLingua

이럴 때:

  • Chain-of-Thought 프롬프트
  • In-Context Learning 예시 다수
  • 질문이 고정돼 있지 않음
  • 극한 압축률(20x)이 필요
LongLLMLingua

이럴 때:

  • RAG 파이프라인
  • 검색된 문서 여러 개를 넣음
  • Lost in the Middle이 의심됨
  • 질문이 항상 함께 옴
LLMLingua-2

이럴 때:

  • 실시간 서비스 (지연 민감)
  • GPU 리소스가 빠듯함
  • 다국어 / 처음 보는 도메인
  • 압축 결과를 캐싱하고 싶음
실무 추천 순서. 대부분의 경우 LLMLingua-2로 시작하는 게 좋습니다. 가장 빠르고, 설정이 단순하고, GPU 부담이 적기 때문입니다. RAG에서 정확도가 아쉬우면 그때 LongLLMLingua를 시도하세요.

4RAG에 LongLLMLingua 적용

검색된 문서 여러 개 + 질문이 있는 전형적인 RAG 상황입니다.

step3_rag.py
from llmlingua import PromptCompressor

llm_lingua = PromptCompressor()          # Llama-2-7b

# 벡터 검색 결과 (문서 리스트)
retrieved_docs = [doc1, doc2, doc3, ...]
question = "우리 회사의 연차 이월 규정은?"

result = llm_lingua.compress_prompt(
    retrieved_docs,                # ★ 리스트로 전달
    question=question,             # ★ 필수
    rate=0.55,

    # ── LongLLMLingua 전용 설정 ──
    condition_in_question="after_condition",   # 질문 인식 압축
    reorder_context="sort",                     # 중요 문서를 앞으로
    dynamic_context_compression_ratio=0.3,       # 동적 압축률 (0.3~0.4)
    condition_compare=True,                     # 대비 기반 정밀 압축
    context_budget="+100",                     # 문서 단위 예산 여유
    rank_method="longllmlingua",               # 문서 랭킹 방식
)

# LLM 호출
final_prompt = result["compressed_prompt"]

파라미터 의미

파라미터역할
condition_in_question"none"/"before"/"after"/"after_condition".
질문을 어디에 두고 조건부 확률을 계산할지
reorder_context"original"(유지) / "sort"(중요도순). Lost in the Middle 대응
dynamic_context_compression_ratio문서별 압축 강도 차등. 0.3~0.4 권장
condition_compare질문 유무 대비로 토큰 중요도 재계산. 정확도↑ 속도↓
context_budget문서 단위 예산. "+100"은 여유 100토큰
rank_methodlongllmlingua, bm25, bge_reranker, cohere 등

5구조 보존 압축 (Structured)

회의록의 화자 이름, 표 헤더처럼 절대 지우면 안 되는 부분이 있을 때 사용합니다. <llmlingua> 태그로 구간을 나누고 구간별 압축률을 지정합니다. 

structured = """
<llmlingua, compress=False>Speaker 4:</llmlingua>
<llmlingua, rate=0.4> Thank you. And can we do the functions for content?</llmlingua>
<llmlingua, compress=False>Speaker 0:</llmlingua>
<llmlingua, rate=0.4> Item 11 is a communication from Council...</llmlingua>
"""

result = llm_lingua.structured_compress_prompt(
    structured, instruction="", question="", rate=0.5)
실무에서 매우 유용합니다. JSON 데이터, 코드, 로그를 압축할 때 키 이름·함수 시그니처는 compress=False로 보존하고 값이나 본문만 압축하는 식으로 쓸 수 있습니다.

7⭐ 품질 검증 — 가장 중요한 단계

압축은 손실(lossy)입니다. "얼마나 줄었나"만 보면 안 되고 "정확도가 얼마나 떨어졌나"를 반드시 측정해야 합니다.

step4_eval.py
# 압축률을 바꿔가며 정확도 곡선을 그린다
for rate in [1.0, 0.8, 0.6, 0.5, 0.4, 0.3]:
    correct = 0
    total_tokens = 0

    for sample in eval_set:
        if rate == 1.0:
            p = sample.prompt                    # 기준선 (무압축)
        else:
            r = llm_lingua.compress_prompt(sample.prompt, rate=rate)
            p = r["compressed_prompt"]
            total_tokens += r["compressed_tokens"]

        answer = call_llm(p)
        correct += (answer == sample.gold)

    print(f"rate={rate}  정확도={correct/len(eval_set):.1%}  토큰={total_tokens}")

2 압축 단계 3종 — 켜고 끄기

LLMLingua는 3개의 필터를 겹쳐 씁니다. 상황에 맞게 조합하세요.

파라미터기본동작
use_context_level_filterTrue 문서 단위 통째 제거. 관련 없는 문서를 버림
use_sentence_level_filterFalse 문장 단위 제거. 문법을 덜 깨뜨려 가독성이 좋음
use_token_level_filterTrue 토큰 단위 제거. 압축률 최고, 문장이 깨짐
문장이 깨지는 게 불편하다면 토큰 필터를 끄고 문장 필터를 켜보세요. 압축률은 낮아지지만 사람이 읽을 수 있는 결과가 나옵니다. 
use_token_level_filter=False,
use_sentence_level_filter=True,

보존(preserve) 관련 파라미터

파라미터용도
force_tokens항상 남길 토큰. ['\n','?','.'] 등 구조 토큰
force_reserve_digit숫자를 강제 보존. 금액·날짜·수치가 중요한 문서에 필수
force_context_ids특정 인덱스의 문서를 무조건 유지
keep_first_sentence / keep_last_sentence각 문서의 앞/뒤 N문장 보존 (주제문·결론 보호)
keep_split원본 구분자(줄바꿈 등) 유지
drop_consecutiveforce_tokens가 연속 등장할 때 중복 제거
숫자 손실은 치명적입니다. 재무 문서·계약서·로그를 압축한다면 force_reserve_digit=True를 꼭 켜세요. $10이 $1이 되는 사고를 막습니다.

4 한계와 주의사항

⚠️ 손실 압축이다

정보가 실제로 사라집니다. 되돌릴 수 없습니다 (LongLLMLingua의 recover()는 응답 후처리일 뿐, 완전 복원이 아님).

⚠️ 사람이 못 읽는다

토큰 단위 삭제라 단어가 깨집니다. 로그·감사 용도로는 원본을 따로 보관해야 합니다.

⚠️ 오버헤드가 있다

압축에도 모델 추론이 필요합니다. 짧은 프롬프트는 압축이 손해입니다.

⚠️ 도메인 의존

제공 모델은 회의록 학습입니다. 코드나 전문 문서는 성능이 떨어질 수 있습니다.

💡 프롬프트 캐싱과의 관계

압축하면 프리픽스가 매번 달라져 provider의 프롬프트 캐시 적중률이 떨어질 수 있습니다. 캐시 절감액과 압축 절감액을 같이 계산하세요.

💡 코드 압축은 신중히

코드는 한 토큰만 사라져도 문법이 깨집니다. 구조 보존 압축이나 AST 기반 방식을 병행하세요.

언제 쓰면 안 되나

  • 법적 효력이 있는 문서 — 계약서 원문을 압축해 판단시키면 안 됨
  • 정확한 인용이 필요한 작업 — 원문 그대로 인용해야 하는 경우
  • 짧은 프롬프트 — 500토큰 미만은 오버헤드가 더 큼
  • 코드 생성·수정 — 문법 깨짐 위험. 구조 보존 압축 필수
  • 이미 캐시 적중률이 높은 워크로드 — 압축이 캐시를 깨뜨릴 수 있음

5 한 장 요약

■ 공통 원리
  작은 모델로 토큰 중요도를 재고, 덜 중요한 토큰을 지운다.
  LLM 재학습 불필요 — 순수 전처리.

■ LLMLingua          (EMNLP'23)
  Perplexity 기반 · 최대 20x 압축
  Budget Controller → Iterative Token → Distribution Align
  → CoT · ICL · 범용

■ LongLLMLingua      (ACL'24)
  질문 인식 + 문서 재정렬 + 동적 압축률 + 서브시퀀스 복원
  RAG 성능 +21.4% (1/4 토큰)
  → RAG · 긴 문서 QA   ※ question 필수

■ LLMLingua-2        (ACL'24 Findings)
  GPT-4 증류 → BERT 토큰 분류기
  3~6배 빠름 · task-agnostic · OOD 견고 · 경량
  → 실시간 서비스 · 다국어 · 캐싱

■ 실무 순서
  1) LLMLingua-2 로 시작 (가장 쉽고 빠름)
  2) rate 를 1.0 → 0.3 으로 낮추며 정확도 곡선 측정
  3) 급락 직전 지점을 운영 기준선으로
  4) RAG 정확도가 아쉬우면 LongLLMLingua 시도
  5) 도메인이 특수하면 자체 데이터로 재학습
가장 중요한 원칙 — 압축률은 목표가 아닙니다. "정확도를 얼마나 유지하면서 비용을 줄였는가"가 유일한 성공 지표입니다. 반드시 평가셋을 만들어 측정한 뒤 배포하세요.
