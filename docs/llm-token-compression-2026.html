LLM 토큰 압축 기술 동향

컨텍스트 윈도우는 100만 토큰 시대로 커졌지만, 비용과 지연시간은 토큰 수에 비례합니다. "얼마나 많이 넣느냐"에서 "얼마나 적게 넣고도 같은 답을 얻느냐"로 경쟁의 축이 이동했습니다. 이 문서는 토큰 압축의 전체 지도를 하이레벨로 정리합니다.

한 문장 정의

컨텍스트 압축이란, LLM에게 매번 보내는 "읽을거리"를 뜻은 유지한 채 분량만 줄이는 일입니다.

LLM은 기억이 없습니다. 매 요청마다 필요한 모든 것(지시문·문서·이전 대화·툴 결과)을 처음부터 다시 통째로 보내야 합니다. 대화가 길어질수록 보내는 양이 눈덩이처럼 불어나고, 요금·속도·정확도가 동시에 나빠집니다. 이걸 막는 기술의 총칭입니다.

B1먼저, 토큰이 무엇인가

토큰은 모델이 글을 세는 단위입니다. 글자도 단어도 아닌, 그 중간쯤의 조각입니다. 요금도 속도도 전부 이 단위로 계산됩니다.

영어는 대체로 "단어 ≈ 토큰"

17자 → 약 10 토큰 · 대략 1.5~2자당 1토큰

실무에서 중요한 사실 — 같은 내용이라도 한국어가 영어보다 토큰을 1.5~3배 더 씁니다. 즉 같은 요금제에서 한국어 서비스가 구조적으로 더 비싸고, 컨텍스트 창도 더 빨리 찹니다. 한국에서 토큰 압축의 체감 효과가 큰 이유입니다.
※ 위 분해는 이해를 돕기 위한 예시이며, 실제 결과는 모델의 토크나이저(cl100k / o200k 등)에 따라 달라집니다.

B2컨텍스트 윈도우 = 모델의 "책상 크기"

모델은 한 번에 펼쳐놓을 수 있는 종이 양이 정해져 있습니다. 이 한도를 컨텍스트 윈도우라고 합니다. 중요한 건 크기가 아니라 그 안을 무엇이 차지하고 있는가입니다.

여기서 핵심 — 사용자가 실제로 입력한 건 2K(전체의 2%)뿐이고, 나머지 98%는 시스템이 알아서 채워 넣은 것입니다. 그래서 "사용자 입력을 줄이자"는 의미가 없고, 시스템이 채우는 90%를 어떻게 다룰지가 전부입니다.

매번 똑같은 부분

시스템 지시, 툴 정의 — 재사용(캐싱)으로 해결. 압축할 필요조차 없습니다.

매번 다른 부분

검색 문서, 툴 실행 결과 — 캐싱이 안 통하므로 압축이 유일한 수단.

계속 쌓이는 부분

대화·툴 이력 — 요약 후 교체(Compaction)로 관리.

B3왜 문제인가 — 대화는 "곱셈"으로 부푼다

가장 많이 오해하는 지점입니다. 대화가 10턴이면 비용도 10배일 것 같지만, 실제로는 훨씬 더 늘어납니다.

① 요금

입력 토큰에 그대로 과금. 위 사례에서 압축·캐싱 없이 하루 1만 대화면 44억 토큰/일.

② 속도

첫 글자가 나오기까지의 시간(TTFT)은 입력 길이에 비례. 길수록 사용자가 기다립니다.

③ 정확도

Lost in the Middle — 컨텍스트가 길수록 중간에 있는 정보를 놓칩니다. 많이 넣는다고 잘하는 게 아닙니다.

가장 반직관적인 사실 — 압축은 비용만 줄이는 게 아니라 정확도를 올리기도 합니다. 관련 없는 문서 9개를 걷어내면 모델이 정답 문서에 집중하기 때문입니다. "압축 = 성능 희생"이라는 전제가 항상 맞지는 않습니다.

B4해결 전략은 딱 3가지뿐

수십 가지 기법이 있어 보이지만, 근본적으로는 세 가지 질문에 답하는 것입니다.

① 덜 넣기

"이걸 굳이 보내야 하나?"

검색 정밀도 개선(문서 10개 → 3개), 툴 정의 슬림화, 로그 필드 제거. 가장 싸고 가장 안전하지만 가장 자주 건너뜁니다.

② 줄여 넣기

"꼭 이 분량이어야 하나?"

요약·발췌·토큰 프루닝. 우리가 흔히 말하는 "압축"이 여기입니다. 효과가 크지만 정보 손실 리스크가 유일하게 존재하는 칸.

③ 다시 안 넣기

"아까 보낸 거 또 보내나?"

프롬프트 캐싱, 상태 저장 대화. 손실이 0인데 절감이 큼 → 무조건 1순위. 단 "매번 똑같은 부분"에만 통합니다.

순서가 중요합니다 — ③ 다시 안 넣기 → ① 덜 넣기 → ② 줄여 넣기. ②를 먼저 하면 ③을 망가뜨립니다(내용이 매번 바뀌어 캐시가 깨짐). 실무에서 가장 흔한 실수입니다.

B5기본 기술 4가지 — 생활 비유로

전문 용어를 걷어내면 우리가 이미 일상에서 쓰는 방법들입니다.

📝

요약 (Abstractive) — "회의록 대신 결론만"

내용을 다시 써서 짧게 만듭니다. 압축률이 가장 높지만 원문 문구는 사라집니다.

원문: 고객이 3월 2일 결제 실패를 겪었고, 카드사 한도 문제로 확인되어 재결제 안내함. 이후 3월 3일 정상 결제 완료됨. (48 tok) ↓ 요약: 3/2 결제실패(카드한도) → 3/3 재결제 완료 (14 tok)
🖍️

발췌 (Extractive) — "교과서에 형광펜"

원문에서 중요한 문장만 그대로 골라냅니다. 문구가 보존되어 인용·감사 대응이 가능합니다.

원문 10문장 중 관련 3문장만 남김 ↓ "제3조 환불은 7일 이내 가능하다." "단, 개봉한 상품은 제외한다." (문구 100% 원본 유지)
🔖

참조·색인 (Reference) — "목차만 주고 필요하면 찾아보게"

원문을 밖에 두고 위치만 알려줍니다. 필요할 때 모델이 다시 꺼내 읽습니다. 손실이 사실상 없습니다.

[대화에 넣는 것] "에러 로그 2,400줄 저장됨 → log_id: a3f9 FATAL 3건, 첫 발생 14:22" (18 tok) [모델이 필요하면] retrieve("a3f9") → 원문 조회
📌

캐싱 (Caching) — "같은 서류는 다시 안 낸다"

바뀌지 않는 앞부분의 계산 결과를 재사용합니다. 내용은 그대로인데 비용만 줄어드는 유일한 무손실 방법.

1회차: [지시 6K][툴 9K][질문] → 전액 과금 2회차: [지시 6K][툴 9K][질문] → 앞 15K 캐시 히트 (50~90% 할인) 조건: 앞부분이 글자 하나까지 동일해야 함

B6같은 입력, 4가지 처리 — 무엇이 남고 무엇이 사라지나

하나의 실제 입력을 네 가지 방식으로 처리했을 때 결과를 나란히 봅니다. 어떤 질문이 들어오느냐에 따라 정답이 달라집니다.

B7초보자가 흔히 하는 오해 6가지

"압축률이 높을수록 좋은 기술이다"
중요한 건 압축률이 아니라 "품질을 유지한 채의" 압축률입니다. 20배 압축해도 답이 틀리면 0점입니다. 반드시 골든셋(정답 세트)으로 압축률-정확도 곡선을 그린 뒤 운영 지점을 정해야 합니다.
"컨텍스트 창이 커졌으니 압축은 필요 없다"
창이 커진 것은 넣을 수 있다는 뜻이지 넣어도 된다는 뜻이 아닙니다. 100만 토큰을 넣으면 요금·지연이 그만큼 늘고 정확도는 오히려 떨어집니다(Lost in the Middle). 창 확대는 압축의 필요성을 키웠습니다.
"압축하면 무조건 성능이 떨어진다"
노이즈 제거형 압축은 정확도를 올리는 경우가 흔합니다. 관련 없는 문서를 걷어내면 모델의 집중도가 올라갑니다. 떨어지는 것은 과도한 압축일 때입니다.
"압축기를 붙이면 그만큼 싸진다"
압축기 자체도 연산을 씁니다. 작은 LM을 돌리는 방식이면 그 추론 비용·지연이 추가됩니다. 프롬프트가 짧으면(2K 미만) 배보다 배꼽이 큽니다. 온프렘에서는 같은 GPU 풀을 나눠 쓰는 점도 함정입니다.
"압축부터 도입하면 된다"
순서가 거꾸로입니다. ① 측정 → ② 프롬프트 순서 정리 → ③ 캐싱 → ④ 압축이 정석입니다. 압축을 먼저 넣으면 매번 내용이 바뀌어 캐싱이 깨지고, 결과적으로 비용이 늘어날 수도 있습니다.
"입력만 줄이면 비용이 해결된다"
추론 모델에서는 출력 단가가 입력의 4~8배입니다(모델별: Claude Sonnet 4.5 5배, GPT-5 8배). 모델이 장황하게 쓰거나 불필요하게 오래 "생각"하면 입력을 아무리 줄여도 청구서가 안 줄어듭니다. 출력 토큰 제어(reasoning_effort·간결성 지시)를 함께 봐야 합니다.

B8용어 사전 — 다음 탭을 읽기 전에

이 표만 이해하면 나머지 탭이 전부 읽힙니다.

토큰 (Token)

모델이 글을 세는 최소 단위. 요금·속도·창 크기의 기준. 한국어는 영어보다 1.5~3배 더 소모.

컨텍스트 윈도우

한 번에 넣을 수 있는 토큰 한도. 입력 + 출력을 합쳐 계산됩니다.

프리필 / 디코드

프리필 = 입력을 읽는 단계(길이에 비례), 디코드 = 답을 한 글자씩 쓰는 단계. 압축은 주로 프리필을 줄입니다.

TTFT

Time To First Token. 첫 글자가 나오기까지의 시간. 입력이 길수록 나빠지는 체감 지표.

KV 캐시

모델이 읽은 내용을 기억해 두는 GPU 메모리 영역. 대화가 길수록 커져 동시 처리량을 제한합니다.

프롬프트(프리픽스) 캐싱

프롬프트 앞부분이 이전과 동일하면 계산을 재사용해 할인. 앞부분이 한 글자만 달라도 무효.

Compaction

대화·툴 이력이 임계치를 넘으면 요약해서 교체하는 것. 에이전트의 표준 생존 기법.

RAG

질문에 맞는 문서를 검색해 프롬프트에 붙여 넣는 방식. 컨텍스트가 커지는 최대 원인이자 압축의 주 무대.

토큰 프루닝

3-BLLMLingua 알고리즘 뜯어보기

L1 압축의 사실상 표준이므로, 무엇을 근거로 토큰을 버리는지를 알아야 어디까지 믿을 수 있는지 판단할 수 있습니다. 세 버전(LLMLingua → LongLLMLingua → LLMLingua-2)은 이름만 비슷할 뿐 작동 원리가 다릅니다.

출발점 — "놀랍지 않은 토큰은 버려도 복원된다"

언어모델은 다음 토큰의 확률을 계산합니다. 어떤 토큰의 확률이 0.98이라면, 그 토큰은 없어도 모델이 알아서 채워 넣습니다. 반대로 확률이 0.02인 토큰은 문맥만으로는 추측이 불가능하므로 진짜 정보입니다.

정보량(self-information)  I(xi) = −log P(xi | x<i) 확률이 낮을수록(=놀라울수록) 정보량이 큽니다. LLMLingua는 이 값이 낮은 토큰부터 지웁니다. "요약"이 아니라 정보이론 기반 선별 삭제라는 점이 핵심입니다.

실제로 스코어를 매기면 이런 모습입니다 — 아래 숫자는 작은 LM이 계산한 토큰별 정보량(개념 예시):

LongLLMLingua — "질문"을 기준으로 다시 계산한다

RAG 특화

v1의 치명적 약점은 질문을 안 본다는 것이었습니다. 같은 문서라도 무엇을 묻느냐에 따라 중요한 부분이 달라지는데, 태스크 무관 PPL은 이를 반영하지 못합니다. LongLLMLingua는 질문 조건부로 신호 자체를 바꿉니다.

대비 정보량(contrastive)  s(xi) = log P(xi | question, x<i)  −  log P(xi | x<i) = 질문 없이 잰 PPL − 질문 주고 잰 PPL. 질문을 알고 나니 훨씬 예측하기 쉬워진 토큰일수록 점수가 높아지고, 그 토큰을 남깁니다. 일반 문맥에서는 흔하지만 이 질문에 대해서만 결정적인 표현이 살아남습니다. 부호에 주의 — 반대로 두면 질문과 무관한 토큰을 남기게 됩니다.

Coarse → Fine 2단 처리

  • Coarse — 문서 단위로 질문 관련도를 매겨 관련 없는 문서를 통째로 탈락
  • Fine — 살아남은 문서 안에서 대비 정보량으로 토큰 프루닝

문서를 먼저 걸러야 토큰 단계 비용이 급감합니다. 리랭커를 앞에 두라는 실무 조언과 같은 이유입니다.

부가 장치 3가지

  • 문서 재정렬 — 중요 문서를 앞으로 이동 → "Lost in the Middle" 완화
  • 동적 압축률 — 상위 문서는 덜, 하위 문서는 더 압축 (예산 차등 배분)
  • Subsequence Recovery — 생성 결과에 등장한 잘린 고유명사·숫자를 원문에서 되찾아 복원
Subsequence Recovery가 실무적으로 중요합니다 — "압축 때문에 계좌번호·날짜가 깨질까?"라는 최대 반론에 대한 알고리즘 차원의 방어막입니다. 압축본에서 손상된 문자열을 원문과 매칭해 출력 단계에서 되살립니다.
대가 — 질문이 바뀌면 압축 결과가 매번 달라집니다. 즉 프롬프트 캐시와 근본적으로 상극입니다. 캐싱이 가능한 구간에는 절대 쓰지 마세요(→ 「구현 가이드」 D2).

    rate=0.5,                      # 목표 비율 (인자명은 ratio 아님)

    force_reserve_digit=True,        # ★ 숫자 포함 토큰 무조건 보존
    drop_consecutive=True,           # force_tokens 가 연달아 반복되면 제거

    # ── LongLLMLingua 전용 (causal LM 경로에서만 동작) ──
    question=q,                     # 질문 인지 활성화 (이 인자가 핵심)
    rank_method="longllmlingua",
    condition_in_question="after_condition",
    context_budget="+100",          # 문서 단계 예산 여유
    dynamic_context_compression_ratio=0.3,  # 순위별 차등 압축
    reorder_context="sort",         # 중요 문서를 앞으로
)
실무에서 가장 자주 사고를 내는 곳 — force_reserve_digit를 켜지 않아 금액·날짜·계좌번호가 잘리는 경우입니다(기본값 False). 숫자가 중요한 도메인이라면 기본으로 켜고 시작하세요. 표·마크다운을 다룬다면 force_tokens에 |·\n을 반드시 넣어야 행 정렬이 유지됩니다.
주의 2가지 — ① 공식 DOCUMENT.md에는 ratio=로 적혀 있지만 실제 인자명은 rate입니다. ② 아래 LongLLMLingua 전용 인자들은 use_llmlingua2=True(인코더 경로)에서는 에러 없이 무시됩니다.

잘 통하는 입력

  • 장황한 산문 — 매뉴얼·정책·회의록·뉴스
  • few-shot 예시가 많은 프롬프트
  • RAG로 끌어온 중복 많은 문서 다발(LongLLMLingua)
  • 같은 표현이 반복되는 보고서류

쓰면 안 되는 입력

  • 코드·설정 파일 — 문법이 깨짐 (→ AST 인지 압축기 사용)
  • 구조화 JSON — 키/값 관계 붕괴 (→ 스키마 테이블화)
  • 법률 조문·계약서 — 문구 그대로가 의미 (→ RECOMP류 추출 요약)
  • 이미 짧은 프롬프트(<2K) — 압축기 비용·지연이 절감액을 초과
정리 — LLMLingua는 "산문에서 예측 가능한 토큰을 골라 지우는" 추출적 압축기입니다. 지어내지 않는다는 점이 최대 강점이고, 구조가 있는 데이터에 약하다는 점이 명확한 한계입니다. 그래서 툴 출력·코드 구간은 §6-B의 타입별 압축(Headroom 등)이 담당하는 서로 다른 영역입니다.

4L2 — 잠재 표현(Latent) 압축

텍스트를 텍스트로 줄이는 대신, 컨텍스트를 소수의 벡터(소프트 토큰)로 인코딩합니다. 이론적 압축률은 가장 높지만 모델 종속적입니다.

Gist Tokens

긴 프롬프트를 소수의 "요약 토큰"으로 증류하도록 모델을 학습. 재사용 가능한 시스템 프롬프트를 극단적으로 압축.

  • 장점: 매우 높은 압축률
  • 단점: 파인튜닝 필요, 모델 종속

ICAE / AutoEncoder

인코더가 컨텍스트를 고정 길이 메모리 슬롯으로 압축하고, 디코더(LLM)가 이를 읽음.

  • 장점: 장기 대화 메모리에 적합
  • 단점: 학습 파이프라인 필요, 해석 불가

xRAG

RAG 문서를 텍스트로 붙이지 않고 임베딩 자체를 모달리티처럼 주입. 검색 문서 1건 = 토큰 몇 개 수준.

  • 장점: RAG 컨텍스트 비용 극적 감소
  • 단점: 정합성/근거 제시(citation) 어려움
실무 판단 — L2는 API 모델(GPT/Claude/Gemini)에서는 사실상 사용 불가합니다. 자체 모델을 파인튜닝·서빙하는 조직만 후보에 올리세요. 대신 개념(“메모리를 압축된 표현으로 유지”)은 에이전트 메모리 설계(L4)에 그대로 응용할 수 있습니다.

5L3 — KV 캐시 압축 (추론 인프라)

자체 모델을 서빙한다면 여기가 진짜 비용 지점입니다. KV 캐시는 컨텍스트 길이에 선형으로 GPU 메모리를 먹으며 동시 처리량을 결정합니다.

계열대표 기법아이디어절감폭도입 난이도
양자화 KIVI, FP8/INT4 KV, TurboQuant Key는 채널별, Value는 토큰별로 저비트 양자화. 재학습 불필요 2~4× 낮음 (설정 플래그)
퇴출/선별 H2O, SnapKV, TOVA, StreamingLLM 어텐션 점수가 높은 "heavy hitter" + 최근 토큰만 유지, 나머지 버림 2~10× 중간
아키텍처 GQA, MQA, MLA (DeepSeek) KV 헤드를 공유하거나 저차원으로 투영. 모델 설계 단계에서 결정 4~14× 높음 (모델 선택 이슈)
메모리 관리 PagedAttention, Prefix Caching (vLLM/SGLang) KV를 페이지 단위로 관리해 파편화 제거 + 공통 프리픽스 재사용 처리량 2~10× 낮음 (엔진 기본 제공)
실무 조합 레시피 — 대부분의 프로덕션은 단일 기법이 아니라 스택으로 씁니다: GQA/MLA 모델 선택 + FP8 KV 양자화 + PagedAttention + Prefix Caching. 여기에 긴 세션·스트리밍 워크로드라면 퇴출(SnapKV 계열)을 추가합니다.

6L4 — 캐싱 & 에이전트 컨텍스트 운영

가장 적은 노력으로 가장 큰 절감을 만드는 레이어. "압축"보다 "재사용"이 먼저입니다.

Prompt Caching (프리픽스 캐싱)

동일한 프롬프트 접두부의 KV 계산 결과를 재사용합니다. 주요 프로바이더가 모두 지원하며 입력 비용 50~90% 할인.

  • OpenAI — 자동 적용 (코드 변경 불필요)
  • Anthropic — cache_control 명시적 마커
  • Gemini — 암묵적 + 명시적 컨텍스트 캐싱
  • 캐시 쓰기 비용은 Anthropic 기준 입력의 1.25배(5분 TTL) → 몇 회만 히트해도 손익분기. OpenAI/Azure는 대체로 무료지만 gpt-5.6+ Standard는 캐시 쓰기도 과금됩니다

단 하나의 설계 규칙

정적인 것을 앞에, 동적인 것을 뒤에.

시스템 프롬프트 → 툴 정의 → 참조 문서 → (여기까지 고정) → 대화 이력 → 사용자 입력 순서. 맨 앞에 타임스탬프·사용자 ID 하나만 들어가도 캐시 히트율 0%가 됩니다.

현장에서 프롬프트 순서만 재정렬해 히트율 80%+ 를 달성하는 사례가 흔합니다.

Semantic Caching

완전 동일이 아니라 의미가 유사한 질의의 응답을 재사용(임베딩 + 벡터 DB). FAQ·검색형에서 효과적.

  • 리스크: 오답 재사용. 유사도 임계값·TTL·무효화 설계 필수

에이전트 Compaction

장시간 실행 에이전트에서 대화·툴 결과가 누적되면 임계치에서 요약 후 교체. 원문은 외부 스토어에 두고 필요 시 재조회.

  • Claude Code / Codex 등 코딩 에이전트의 표준 패턴

구조적 절감

툴 정의 슬림화, 로그/JSON 필드 제거, 관측치 truncation, 모델 라우팅(쉬운 요청은 소형 모델), Batch API(50% 할인).

  • 압축 알고리즘보다 먼저 해야 할 일

6-B · 툴 호출(Tool Use) 출력 압축 — 에이전트의 실제 병목

코딩·SRE 에이전트에서 컨텍스트를 잡아먹는 것은 사람이 쓴 프롬프트가 아니라 툴이 뱉은 출력입니다. grep 100건, kubectl logs 3천 줄, GitHub API JSON 응답, 파일 전문 — 이것들이 대화에 그대로 누적되며, 프롬프트 캐싱으로는 해결되지 않습니다(매번 내용이 다르므로).

왜 캐싱이 안 통하나 — 툴 출력은 ①매 호출마다 내용이 다르고, ②대화 중간에 삽입되어 그 뒤 모든 토큰의 캐시 프리픽스를 깨뜨립니다. 즉 툴 출력 구간은 L4(재사용)가 아니라 L1(압축)으로 풀어야 하는 영역입니다.

Headroom headroomlabs-ai/headroom 주목

"AI 에이전트를 위한 컨텍스트 압축 레이어"를 표방하는 Apache-2.0 OSS. 에이전트가 읽는 모든 것 (툴 출력·로그·RAG 청크·파일·대화 이력)을 LLM에 도달하기 전에 압축합니다. LLMLingua가 산문 프롬프트 압축 라이브러리라면, Headroom은 에이전트 런타임 전체를 감싸는 파이프라인이라는 점이 결정적 차이입니다.

  • 4가지 주요 투입 방식 — 라이브러리(compress()) · 로컬 프록시(코드 변경 0) · headroom wrap <agent> · MCP 서버(headroom mcp serve)
    이 밖에도 크로스 에이전트 메모리, headroom learn(실패 세션에서 교정 규칙 학습), 이미지 압축(40~90%) 등을 제공
  • 로컬 우선(local-first) — 압축이 사용자 머신에서 수행되어 원문이 외부로 나가지 않음 → 온프렘/보안 요건과 궁합
  • 가역(Reversible, CCR) — 원문을 로컬에 캐싱하고, 모델이 필요하면 headroom_retrieve로 되찾음 → 정보 손실 리스크를 구조적으로 완화

내부 구조 — 콘텐츠 타입별 라우팅

단일 알고리즘이 아니라, 콘텐츠를 판별해 전용 압축기로 보내는 구조입니다.

  • ContentRouter — 입력 종류를 감지해 압축기 선택
  • SmartCrusher — JSON 전용(배열/중첩/혼합 타입). 툴 응답에 가장 효과적
  • CodeCompressor — AST 인지 (Python·JS/TS·Go·Rust·Java·C/C++·Perl)
  • Kompress-v2-base — 에이전트 트레이스로 학습된 자체 HF 모델(산문 담당)
  • CacheAligner — 프로바이더 KV 캐시 프리픽스를 깨뜨릴 휘발성 콘텐츠를 탐지·경고(프롬프트를 임의로 고쳐 쓰지 않음)
  • Live-zone 압축 — 새로 들어온 바이트만 압축하고 고정 프리픽스는 바이트 단위로 보존 → 압축하면서도 캐시를 깨지 않음. 이력을 버리지 않음(drop 아님)

출력 토큰까지 줄이는 접근 — 흔치 않은 설계

대부분의 압축 도구가 보내는 토큰만 다루는 반면, Headroom은 모델이 써 내려오는 토큰도 줄입니다. 추론 모델에서 출력 단가가 입력의 4~8배인 점을 노린 설계입니다.

  • Verbosity steering — "장황하지 말고 맥락을 재진술하지 말라"는 짧은 지시를 시스템 프롬프트 맨 뒤에 덧붙임 → 프롬프트 캐시는 그대로 히트
  • Effort routing — 툴 결과를 받아 단순 재개하는 턴은 사고 강도를 낮추고, 새 질문·에러에는 full effort 유지
    OpenAI reasoning_effort / Anthropic thinking.budget_tokens·output_config.effort에 매핑 → Azure 탭 A2의 출력 제어와 동일한 레버
  • 홀드아웃 측정 — 출력 절감은 반사실(counterfactual)이라 기본값은 추정치입니다(Reduction: 31.7% (95% CI 27.7…35.7) [estimated]). HEADROOM_OUTPUT_HOLDOUT=0.1로 10%를 대조군으로 남기면 실측(measured) 값으로 전환됩니다.

참고할 점 — 절감치를 단정하지 않고 측정 방법론과 불확실성을 명시하는 태도는, 사내 과제에서 압축 효과를 보고할 때 그대로 차용할 만합니다.

Q. 프롬프트의 상당 부분이 매 요청마다 동일한가?
YES → 압축보다 Prompt Caching이 먼저. 정적/동적 분리 후 순서 재정렬만으로 50~90% 절감. 압축은 그 다음.

YES → 캐싱이 안 먹힘. LongLLMLingua 같은 쿼리 인지 압축이 정답 구간.
Q. 원문 문구를 그대로 보존해야 하는가? (법률/규정/감사)
YES → 토큰 프루닝 금지. RECOMP 류 추출 요약 또는 검색 정밀도 개선으로 접근.
Q. 모델을 직접 서빙하는가?
YES → L3 KV 캐시 최적화가 최대 ROI. vLLM + FP8 KV + Prefix Caching부터. NO(API) → L1 + L4에 집중.

"압축"이라 부르지만 압축이 아닌 것들

Truncation (잘라내기)

앞/뒤를 그냥 버리는 것. 토큰은 줄지만 무엇을 버릴지 판단하지 않습니다. 압축이 아니라 포기에 가깝습니다.

Caching (캐싱)

토큰 수는 그대로입니다. 단가만 내려갑니다. 컨텍스트 창 압박에는 전혀 도움이 안 됩니다.

Retrieval (검색)

애초에 덜 넣는 것. 이미 넣은 것을 줄이는 압축과는 다른 축입니다. 다만 실무에서는 가장 효과가 큽니다.

C2분류 체계 — 5개 축으로 좌표를 잡는다

논문·라이브러리를 볼 때 이 5개 축만 확인하면 성격이 즉시 파악됩니다.

축 1 · 압축 대상

시스템 프롬프트 / RAG 문서 / 대화 이력 / 툴 출력 / KV 상태. 대상이 다르면 통하는 기법이 완전히 다릅니다.

축 2 · 결과물 형태

하드(텍스트) = 어느 모델에나 붙음 · 디버깅 가능. 소프트(벡터) = 압축률 최고 · 모델 종속 · API 모델 불가.

축 3 · 선택 방식

추출적 = 원문 조각을 고름 → 환각 없음. 추상적 = 새로 씀 → 압축률 높지만 환각·왜곡 가능.

축 4 · 질문 인식

질문 무관(query-agnostic) = 결과 재사용·캐싱 가능. 질문 조건부(query-aware) = 압축률 높지만 매번 달라져 캐시가 깨짐.

축 5 · 학습 필요 여부

Training-free = 바로 적용. 학습 필요 = 파인튜닝·증류 파이프라인 필요, 모델 바뀌면 다시.

파생 축 · 압축 시점

오프라인(사전 압축·캐시 가능) vs 온라인(요청 시 실시간 → 지연 추가). 이 차이가 실제 손익을 가릅니다.

① 압축률　CR = Torig / Tcomp 가장 쉽게 좋아 보이는 숫자. 단독으로는 아무 의미가 없습니다.
② 성능 유지율　R = Acccomp / Accorig 같은 골든셋을 압축 전/후로 돌린 정확도의 비. 평균과 함께 최악 케이스(p5)를 반드시 병기하세요.
③ 순 지연　ΔT = tcompress + tprefill(comp) − tprefill(orig) ΔT > 0 이면 압축했는데 더 느려진 것입니다. 온라인 압축에서 실제로 자주 발생합니다.
④ 순 절감　ΔC = (Torig − Tcomp) × Pin − Ccompressor Ccompressor = 압축기 자체 비용(LLM 요약이면 토큰비, LLMLingua면 GPU 시간). 이걸 빼지 않은 절감 보고는 전부 과대계상입니다.
손익분기 — 압축이 이득이 되는 조건은 Ccompressor < (Torig − Tcomp) × Pin 입니다. 압축 결과를 N번 재사용하면 좌변이 C/N이 되어 급격히 유리해집니다. → 재사용되는 것(시스템 프롬프트, 대화 이력, 자주 조회되는 문서)을 우선 압축하는 것이 정석인 이유입니다.

압축기 비용과 캐시 히트 상실분을 빼야 합니다. 특히 질문 조건부 압축(LongLLMLingua 등)은 프리픽스를 매번 바꿔 프롬프트 캐시를 깨뜨리므로, 캐시가 잘 듣던 워크로드에서는 오히려 비용이 늘 수 있습니다.
"입력 토큰만 측정하면 된다"
출력 토큰은 대체로 입력보다 4~8배 비쌉니다(모델별 상이). 압축이 출력 길이에 영향을 주는 경우도 있으므로 입력·출력·캐시 읽기·캐시 쓰기를 각각 기록하세요.
"골든셋은 있으니 그걸로 검증하면 된다"
기존 골든셋은 대개 쉬운 케이스 위주입니다. 압축 검증용으로는 숫자·부정어·예외조항·긴 이력·유사 문서 다수가 포함된 케이스를 일부러 추가해야 의미가 있습니다.
"오프라인 벤치마크에서 좋았으니 배포한다"
벤치마크 입력은 정제되어 있고 실제 트래픽은 지저분합니다. 섀도 모드(압축본·원본 동시 호출 후 결과 비교)로 실트래픽 표본을 며칠 돌린 뒤 비율 롤아웃하세요.

최소 평가 세트 — 이 정도는 있어야 켤 수 있다

  • 수치·단위 케이스 — 금액, 비율, 날짜, 수량이 답에 직접 들어가는 질문 (숫자 절단·단위 소실 탐지)
  • 부정·예외 케이스 — "~를 제외하고", "~하지 않는 경우", "단, ~인 때에는" (결론 반전 탐지)
  • 고유명사·ID 케이스 — 상품코드, 주문번호, 사람 이름 (파편화·오타 탐지)
  • 긴 이력 케이스 — 10턴 이상 대화 후 초반 정보를 묻는 질문 (이력 압축 손실 탐지)
  • 유사 문서 다수 — 비슷한 문서 5건 중 1건만 정답 (오답 문서 생존 탐지)
  • 표·코드 케이스 — 구조가 깨지면 즉시 드러나는 입력 (구조 파괴 탐지)
  • 압축 무효 케이스 — 원래 짧은 입력 (압축이 손해인 구간 확인)
기록해 둘 것 — 평가 시 원문·압축본·모델 응답을 세트로 로깅하세요. 나중에 품질 이슈가 났을 때 "압축 때문인가, 모델 때문인가, 검색 때문인가"를 구분할 수 있는 유일한 방법입니다. 압축본을 남기지 않으면 원인 규명이 사실상 불가능해집니다.

C7파이프라인 설계 — 어디에, 어떤 순서로 붙이나

압축은 "라이브러리 하나 끼우기"가 아니라 컨텍스트를 구간으로 나누고 구간별로 다른 처리를 거는 일입니다. 구간을 안 나누면 캐시가 깨지거나 중요한 것이 잘립니다.

1단계 — 컨텍스트를 3구간으로 자른다

구간내용변경 빈도여기에 걸 처리절대 하면 안 되는 것
① 정적
STATIC		 시스템 프롬프트, 역할 정의, 툴 스키마, 고정 예시 거의 없음 캐싱 + 1회성 수동 정리 동적 압축 금지 — 매번 바뀌면 캐시가 전부 미스
② 준정적
SEMI		 대화 이력, 사용자 프로필, 세션 상태 턴마다 증가 상태 접기 + 슬라이딩 윈도우 매 턴 전체 재요약 — 앞부분이 계속 바뀌어 캐시 파괴
③ 동적
DYNAMIC		 RAG 검색 결과, 툴 출력, 현재 질문 매 요청 손실 압축 전면 허용 —
단 하나의 배치 규칙 — [정적] → [준정적] → [동적] 순서를 절대 바꾸지 마세요. 프롬프트 캐시는 앞에서부터 일치하는 구간만 재사용합니다. 동적인 것을 앞에 두면 뒤가 전부 캐시 미스가 됩니다. 압축을 아무리 잘해도 이 순서를 어기면 비용이 늘어납니다.

def build_context(system, history, docs, tools_out, question,
                  budget=8000):
    # ── 정적: 손대지 않는다 (캐시 대상) ─────────────
    head = system                      # 그대로

    # ── 무손실 3종: 항상 적용 ──────────────────────
    tools_out = whitelist(tools_out, ALLOWED_FIELDS)   # STEP 1
    tools_out = to_table(tools_out)                    # STEP 2
    docs      = to_handles(docs, min_tokens=1000)      # STEP 3

    # ── 준정적: 상태로 접기 (요약 아님) ─────────────
    hist = fold_state(history, keep_recent=4)

    body = join(hist, docs, tools_out, question)
    used = count_tokens(head) + count_tokens(body)

    # ── 예산 이내면 여기서 종료: 손실 압축 안 함 ─────
    if used <= budget:
        return head + body

    # ── STEP 4: 관련 청크만 (추출적, 환각 없음) ──────
    body = select_chunks(body, question, target=budget)
    if count_tokens(head) + count_tokens(body) <= budget:
        return head + body

    # ── STEP 5: 최후 수단. 보호 토큰 지정 필수 ───────
    body = prune_tokens(
        body,
        target_token=budget - count_tokens(head),
        force_tokens=["\n", ".", "?", "않", "제외", "단"],
        force_reserve_digit=True,          # 숫자 보호
    )
    return head + body
핵심은 조기 반환 2개입니다. 예산 안에 들어오면 손실 압축을 아예 실행하지 않습니다. 대부분의 요청은 STEP 3에서 끝나고, 손실 압축은 긴 요청에만 걸립니다 — 리스크가 노출되는 트래픽 비중이 크게 줄어듭니다.

3단계 — 안전장치를 함께 붙인다

보호 토큰 목록

숫자·통화·부정어·ID 패턴은 압축 대상에서 제외. 정규식으로 사전 마스킹 후 복원하는 방식이 가장 확실합니다.

롤백 스위치

압축을 런타임 플래그로 끌 수 있게. 품질 사고 시 배포 없이 즉시 원복할 수 있어야 합니다.

이중 로깅

원문 / 압축본 / 응답 / 압축률 / 소요시간을 한 세트로. 샘플링(예: 1%)만 해도 충분합니다.

C9한 장 요약 — 압축만 놓고 본 결론

Bottom line

토큰 압축의 실질 성과는 손실 압축 알고리즘의 성능이 아니라, 무손실 구간을 얼마나 짜냈는가에서 대부분 결정됩니다.

화이트리스트 · 구조 변환 · 참조 핸들 · 상태 접기 네 가지만으로 통상 2~4배가 나오고, 이 구간은 품질 리스크가 사실상 없습니다. LLMLingua 같은 손실 압축은 그 이후에 남는 초과분을 처리하는 마지막 단계로 두는 것이 맞습니다.

손실 압축을 켜도 되는 조건

  • 무손실 4종을 이미 적용했고 여전히 예산 초과
  • 입력이 2,000토큰 이상이고 중복이 많은 자연어
  • 회귀 세트(C6)가 준비되어 있고 기준선 수치가 있다
  • 원문/압축본 이중 로깅이 켜져 있다
  • 런타임에서 즉시 끌 수 있다
  • 압축 대상이 동적 구간이며 캐시 경계를 침범하지 않는다

켜면 안 되는 경우

  • 입력이 짧다(수백 토큰) — 압축기 비용이 절감을 초과
  • 대상이 코드·표·설정·수치 데이터
  • 법령·계약·의료 등 근거 증빙이 필요한 도메인
  • 프롬프트 캐시 히트율이 이미 높다 — 압축이 캐시를 깨서 손해
  • 정확도 기준선을 측정한 적이 없다
  • 시스템 프롬프트 등 정적 구간이다

실행 순서 요약

순서할 일기대 효과리스크
0컨텍스트 구간 분리 + 토큰 계측 + 골든셋 확보—없음
1정적/동적 순서 정렬 → 프롬프트 캐시 적용단가 ↓없음
2툴 출력 화이트리스트 + 구조 변환토큰 30~60% ↓없음
3큰 본문 참조 핸들화툴 구간 대폭 ↓왕복 1회 추가
4대화 이력 상태 접기 + 슬라이딩 윈도우이력 2~4× ↓낮음
5RAG 결과 추출적 선택(리랭크 + top-k)문서 3~5× ↓근거 누락
6초과분에만 토큰 프루닝 (보호 토큰 필수)잔여 2~3× ↓품질 회귀
7자체 서빙이라면 KV 압축 검토처리량 ↑ (요금 무관)인프라 작업
가장 자주 하는 실수를 한 줄로 — 6번부터 시작하는 것입니다. 0~4번은 리스크 없이 절반 이상을 줄이고, 5~6번은 리스크를 지고 나머지를 줄입니다. 순서를 지키면 대부분의 조직은 6번까지 갈 필요조차 없습니다.

"우리 서비스에 컨텍스트 압축을 어떻게 붙이나"에 대한 실행 문서입니다. 개념은 「기초 개념」, 판단은 「전략 판단」 탭을 보세요.

D1먼저 할 일 — 컨텍스트 예산 계측

가장 흔한 실패는 어디가 큰지 모른 채 압축부터 붙이는 것입니다. 요청 하나를 구성 요소별로 분해해 로그를 남기는 것부터 시작합니다.

요청 조립 지점에 계측 심기 python
import tiktoken, json, logging

enc = tiktoken.get_encoding("o200k_base")
def ntok(x): return len(enc.encode(x if isinstance(x, str) else json.dumps(x, ensure_ascii=False)))

def build_request(sys_prompt, tools, docs, history, question):
    parts = {
        "system":   ntok(sys_prompt),
        "tools":    ntok(tools),        # 툴 정의도 토큰이다 — 자주 누락
        "docs":     ntok(docs),         # RAG 검색 결과
        "history":  ntok(history),      # 대화 + 툴 실행 결과
        "question": ntok(question),
    }
    total = sum(parts.values())
    logging.info("ctx_budget", extra={
        "parts": parts,
        "total": total,
        "static_ratio": (parts["system"]+parts["tools"]) / total,   # → 캐싱 가능 비중
        "volatile_ratio": (parts["docs"]+parts["history"]) / total, # → 압축 대상 비중
    })
    return parts, total
이 두 비율이 전략을 결정합니다. static_ratio가 높으면 캐싱이 답이고, volatile_ratio가 높으면 압축이 답입니다. 추측하지 말고 일주일치 로그로 확인하세요.

필수 지표 1 — 캐시 히트율

cached_tokens ÷ 전체 입력 토큰 (Responses API는 input_tokens_details, Chat Completions는 prompt_tokens_details). 80% 미만이면 압축보다 캐싱 정비가 우선입니다.

필수 지표 2 — 입력/출력 비중

이력 관리 — Compaction 루프

준손실

대화·툴 이력이 임계치를 넘으면 요약으로 교체합니다. 에이전트라면 사실상 필수입니다.

직접 구현하는 Compaction 루프 python
THRESHOLD = 0.7     # 창의 70% 차면 압축
KEEP_RECENT = 3    # 최근 N턴은 원문 유지 (중요)

def maybe_compact(history, window):
    if ntok(history) < window * THRESHOLD:
        return history

    old, recent = history[:-KEEP_RECENT], history[-KEEP_RECENT:]
    summary = cheap_llm(                     # 요약은 저렴한 모델로
        "다음 작업 로그를 상태 노트로 압축하라. "
        "목표 / 확정 사실 / 수정 내역 / 남은 작업 / 참조 ID만 남길 것. "
        "추측 금지, 원문에 없는 내용 생성 금지.", old)

    archive_id = store.put(old)              # 원문은 버리지 말고 보관
    return [{"role":"system",
             "content": f"[진행 상태]\n{summary}\n[원문: {archive_id}]"},
            *recent]
3가지 필수 안전장치 — ① 최근 N턴은 원문 유지(직전 맥락 손실이 가장 치명적) ② 원문 아카이브 후 ID를 남겨 재조회 가능하게 ③ 요약 프롬프트에 "추측 금지" 명시.
직접 만들기 전에 — Azure Responses API는 context_management.compact_threshold로 이 루프를 서버가 대신 돌려줍니다(→「Azure 제공 기능」 탭 A4). 관리형이 가능하면 직접 구현하지 마세요.

손실

LongLLMLingua — 쿼리 인지 압축 (RAG 경로) python
from llmlingua import PromptCompressor

# ★ LongLLMLingua(질문 인지)는 causal LM 경로입니다.
#   use_llmlingua2=True 로 두면 question/rank_method 가
#   조용히 무시되므로 반드시 분리하세요.
compressor = PromptCompressor(
    model_name="NousResearch/Llama-2-7b-hf",   # 기본값
)

def compress_docs(docs: list[str], question: str, budget: int):
    if ntok("\n".join(docs)) < 2000:
        return docs                      # 짧으면 압축이 손해
    r = compressor.compress_prompt(
        docs,
        question=question,              # ← 질문 기준으로 중요도 판단
        target_token=budget,
        force_tokens=["\n","?",":"],   # 구조 토큰 보존
        condition_in_question="after_condition",
        rank_method="longllmlingua",
    )
    return r["compressed_prompt"]

# 질문이 없는 범용 압축이라면 LLMLingua-2 (빠르고 저렴)
# PromptCompressor(
#   "microsoft/llmlingua-2-xlm-roberta-large-meetingbank",
#   use_llmlingua2=True)
가장 흔한 함정 — use_llmlingua2=True 상태에서 question·rank_method·reorder_context·dynamic_context_compression_ratio를 넘기면 에러 없이 무시됩니다. LLMLingua-2는 태스크 무관 압축기이기 때문입니다. 쿼리 인지가 필요하면 causal LM 경로를 쓰세요(대신 훨씬 느립니다).
2K 미만 가드도 중요합니다. 짧은 프롬프트는 압축기 실행 비용·지연이 절감액을 넘습니다. 또한 압축기 자체가 GPU/CPU를 소비하므로 온프렘에서는 같은 자원 풀을 나눠 쓴다는 점을 계산에 넣어야 합니다.

D4품질 회귀 방지 — 압축을 켜기 전 반드시

손실 압축은 조용히 틀립니다. 에러가 안 나고 그럴듯한 답이 나오므로, 자동 검증 없이는 사고를 인지할 수 없습니다.

압축률-정확도 곡선을 그려 운영 지점 결정 python
# 골든셋: 질문 + 정답(또는 정답 포함 근거) 100~300건
GOLDEN = load("golden.jsonl")

for ratio in [1.0, 0.7, 0.5, 0.35, 0.25]:
    ok = tok = 0
    for case in GOLDEN:
        ctx = compress(case.docs, case.q, ratio) if ratio < 1 else case.docs
        ans = llm(case.q, ctx)
        ok  += judge(ans, case.answer)     # 정확 일치 or LLM-as-judge
        tok += ntok(ctx)
    print(f"ratio={ratio} acc={ok/len(GOLDEN):.3f} tok={tok}")

# 출력 예 ─ 이 표를 보고 운영 지점을 정한다
# ratio=1.00  acc=0.910  tok=412,000   (기준선)
# ratio=0.70  acc=0.908  tok=289,000   ← 무해
# ratio=0.50  acc=0.902  tok=206,000   ← 권장 운영점
# ratio=0.35  acc=0.871  tok=144,000   ← 손실 시작
# ratio=0.25  acc=0.780  tok=103,000   ← 절벽
"절벽"을 찾는 것이 목적입니다. 정확도가 급락하기 직전 지점의 한 단계 앞을 운영값으로 삼으세요. 골든셋 없이 압축률을 정하는 것은 눈 감고 운전하는 것과 같습니다.

반드시 넣어야 할 회귀 케이스

  • 숫자·날짜·ID 추출 — 압축이 가장 자주 망가뜨리는 유형
  • 부정문 — "환불 불가"가 "환불 가능"으로 뒤집히는 사고
  • 다중 조건 — "A이면서 B가 아닐 때" 류의 복합 조건
  • 표·목록 구조 — 행 정렬이 어긋나면 값이 뒤바뀜
  • 긴 컨텍스트 중간의 정답 — Lost in the Middle 검증

운영 중 감시 지표

  • 압축률 분포 — 갑자기 튀면 입력 성격이 바뀐 신호
  • retrieve 호출률 — 급증 = 과압축. 모델이 계속 되찾고 있음
  • 캐시 히트율 — 하락 = 누군가 프롬프트 앞부분을 건드림
  • 재질문율 / 대화 길이 — 품질 저하의 선행 지표
  • 홀드아웃 5~10% — 압축 미적용 대조군으로 실측 비교
롤백 스위치를 먼저 만드세요 — 압축은 기능 플래그로 즉시 끌 수 있어야 합니다. 테넌트·엔드포인트 단위로 on/off가 가능해야 사고 시 영향 범위를 좁힐 수 있습니다.

D5도입 체크리스트

위에서부터 순서대로 체크하세요. 파란 항목은 건너뛰면 안 되는 필수입니다.

착수 전

  • 구성 요소별 토큰 로그를 남기고 있다 (system/tools/docs/history/question)
  • 캐시 히트율을 측정하고 있다 (cached_tokens)
  • 입력 : 출력 비용 비중을 알고 있다
  • p50이 아니라 p95 컨텍스트 길이를 안다
  • 골든셋 100건 이상을 확보했다
  • 기능 플래그로 압축을 끌 수 있다

무손실 단계 (먼저)

  • 프롬프트 정적 → 동적 순으로 조립했다
  • 시스템 프롬프트 버전을 고정했다 (잦은 수정 금지)
  • RAG top_k 를 재검토하고 리랭커를 넣었다
  • 툴 정의를 슬림화했다 (15개 초과 시 그룹핑/검색)
  • 툴 결과에 필드 화이트리스트를 적용했다
  • 프로바이더 캐싱을 활성화하고 히트를 확인했다

이력 관리

  • Compaction 임계치를 정했다 (창의 60~75%)
  • 최근 N턴은 원문 유지하도록 했다
  • 압축 전 원문을 아카이브하고 ID를 남긴다
  • 고정 상태 블록(확정 사실)을 분리했다
  • 관리형 Compaction(Azure 등) 사용 가능 여부를 확인했다

손실 압축 도입 시

  • 압축률-정확도 곡선을 그렸다
  • "절벽" 직전보다 한 단계 보수적으로 설정했다
  • 짧은 입력(<2K)은 압축을 건너뛴다
  • 압축기 자체의 비용·지연을 계산에 넣었다
  • 숫자·부정문·표 회귀 케이스를 넣었다
  • 홀드아웃 대조군을 5~10% 남겼다
  • retrieve 호출률을 모니터링한다 (과압축 탐지)

D6안티패턴 — 실제로 자주 나오는 실수

캐싱보다 압축을 먼저 붙였다
압축은 프롬프트 내용을 매번 바꾸므로 캐시를 깨뜨립니다. 무손실 절감(캐싱)을 손실 절감(압축)으로 맞바꾼 셈이라, 비용이 오히려 늘 수 있습니다. 순서: 캐싱 → 압축.
시스템 프롬프트 맨 앞에 타임스탬프·사용자 ID를 넣었다
한 줄 때문에 뒤의 모든 토큰이 캐시 대상에서 제외됩니다. 변동 값은 반드시 뒤쪽 메시지로 옮기세요. 히트율 0% 사례의 대부분이 이 원인입니다.
툴 응답 JSON을 json.dumps() 그대로 넣었다
키가 레코드마다 반복되고 대부분의 필드는 모델이 쓰지 않습니다. 화이트리스트 + 테이블화만으로 5~10배가 줄어듭니다. 압축 라이브러리보다 먼저 할 일입니다.
압축했는데 원문을 버렸다
되돌릴 수 없으면 모든 압축 판단이 영구적 도박이 됩니다. 원문은 반드시 보관하고 ref_id를 남기세요. 저장 비용은 토큰 비용에 비해 무시할 수준입니다.
압축률을 감으로 정했다 ("일단 50%")
같은 50%라도 도메인마다 절벽 위치가 다릅니다. 법률·의료 텍스트는 0.7에서 이미 깨지고, 로그·JSON은 0.2도 안전합니다. 골든셋으로 실측하세요.
전체 대화를 한 번에 요약해 교체했다
직전 턴 맥락이 사라져 모델이 방금 한 일을 다시 합니다. 최근 N턴은 원문 유지가 원칙입니다.
시맨틱 캐시를 테넌트 구분 없이 켰다
A사 질문의 답이 B사에 나갈 수 있습니다. 보안 사고입니다. 네임스페이스 분리와 개인화 응답 제외를 반드시 함께 설계하세요.
압축 효과를 "추정치"로만 보고했다
홀드아웃 대조군 없이는 실제 절감을 증명할 수 없습니다. 5~10%를 미적용으로 남겨 측정값으로 보고하세요.

Executive Summary

토큰 압축은 "독립된 장기 R&D 과제"로 가져갈 만한 주제는 아닙니다. 단, 컨텍스트 효율화 플랫폼의 상시 모듈로는 반드시 필요합니다.

이유는 셋입니다. ① 동일 비용을 아끼는 데 캐싱·라우팅·경량모델보다 투입 대비 절감폭이 작고 검증 부담이 큽니다. ② 핵심 알고리즘이 이미 오픈소스로 상용화되어 차별화 여지가 좁습니다. ③ 단, 온프렘 환경에서는 논리가 달라집니다 — 압축이 "비용"이 아니라 "GPU 용량"을 푸는 수단이 되기 때문입니다. 이 부분이 KT 맥락의 핵심 분기점입니다.

토큰 압축 (L1)▼ 하락 압력 — 중기

약화 요인: 토큰 단가의 지속 하락, 프로바이더의 캐싱·컨텍스트 기능 내장 확대, 압축 알고리즘의 OSS 범용화(차별화 소멸), 게이트웨이 기본 기능으로 흡수.
상쇄 요인: 에이전트 워크로드의 토큰 폭증, 롱컨텍스트 품질 저하(lost-in-the-middle) 문제는 계속 존재.
순판단: 기능 자체는 살아남지만 "독립 과제"로서의 가치는 축소. 플랫폼 모듈로 편입이 정답.

모델 라우팅▲ 상승 — 장기

모델 종류·가격대가 계속 늘어날수록 라우팅의 가치는 커집니다. 라우팅 정책과 난이도 분류 데이터는 조직 고유 자산으로 축적되며, 모델이 바뀌어도 재사용됩니다.

경량모델 / 파인튜닝▲ 상승 — 장기

오픈웨이트 모델의 품질이 프론티어에 근접하며 도메인 특화 SLM의 경쟁력이 커집니다. 무엇보다 파인튜닝은 긴 시스템 프롬프트를 가중치로 이전하는 것 — 사실상 압축의 상위 호환입니다.

온프렘 / 데이터 주권▲ 상승 — 장기

기술이 아니라 규제와 계약이 수요를 만듭니다. 금융·공공·통신 영역에서는 모델 성능과 무관하게 요구가 유지되며, 인프라와 운영 노하우는 그대로 자산이 됩니다.

프롬프트 캐싱= 유지 — 표준화 완료

이미 모든 주요 프로바이더의 기본 기능입니다. 차별화 요소는 아니고 안 하면 손해인 위생 항목. 다만 온프렘에서는 캐시 정책을 직접 통제할 수 있어 여전히 설계 여지가 있습니다.

S5그럼에도 토큰 압축이 정답인 조건

압축이 "필수"가 되는 구간은 분명히 존재합니다. 아래 왼쪽에 해당하면 다른 대안으로 대체 불가입니다.

압축이 유효 — 대체 수단 없음

  • 캐싱이 안 먹히는 워크로드 — 매 요청 컨텍스트가 완전히 달라지는 RAG·멀티홉 에이전트. 프리픽스가 재사용되지 않으므로 캐싱 절감이 0에 수렴
  • 컨텍스트 윈도우 물리적 초과 — 검색 문서가 창을 넘어설 때. 비용 문제가 아니라 동작 여부의 문제
  • 롱컨텍스트 품질 저하 — 노이즈 문서 제거가 정확도를 올리는 경우. 압축이 비용이 아닌 품질 수단
  • 온프렘 GPU 용량 고정 — 단가가 아니라 처리량이 제약. 입력이 짧아지면 동시 처리 요청 수가 직접 늘어남
  • 이미 최저가 모델을 쓰는 경우 — 라우팅·SLM 카드를 이미 소진해 남은 레버가 토큰 수뿐
  • 툴을 많이 호출하는 에이전트 — 컨텍스트의 다수가 툴이 뱉은 출력(로그·JSON·파일)이며 매번 내용이 달라 캐싱 불가. 라우팅·SLM으로도 대체 안 되는 구간 (→ 탭1 §6-B)

압축이 비효율 — 다른 것부터

  • 프롬프트 대부분이 정적 — 캐싱으로 90% 해결. 압축은 오히려 캐시를 깨뜨려 역효과
  • 프롬프트가 짧음(< 2K 토큰) — 압축기 실행 비용이 절감액을 초과하는 구간
  • 정확 인용·수치 추출이 핵심 — 손실 압축의 리스크가 절감액보다 큼(감사·규제 대응 불가)
  • 지연시간이 최우선 SLA — 압축 단계가 TTFT를 늘릴 수 있음
  • 비용 대부분이 출력 토큰 — 입력 압축은 효과 없음. CoT 압축이나 모델 교체가 답
가장 중요한 분기 — API를 쓰는가, 온프렘을 쓰는가에 따라 압축의 의미가 완전히 달라집니다. API에서는 압축 = 비용 절감(대안 많음). 온프렘에서는 압축 = 용량 확보(대안 적음).

S6온프렘 데이터 환경에서는 계산이 달라진다

자체 인프라에서는 "토큰당 얼마"가 아니라 "GPU를 몇 초 점유하는가"가 비용입니다. 이 전환이 우선순위를 바꿉니다.

API 환경의 비용 구조

  • 비용 = 토큰 수 × 공시 단가 (완전 변동비)
  • 레버: 단가(라우팅/SLM) > 토큰 수(압축)
  • 토큰 단가가 계속 하락 → 압축 ROI도 함께 하락
  • 캐싱은 프로바이더 정책에 종속 (기본 TTL 5~10분, 옵션으로 1시간·24시간 연장 가능)

온프렘 환경의 비용 구조

  • 비용 = GPU 감가상각 + 전력 (거의 고정비)
  • 레버: 처리량(동시 요청 수) — 즉 KV 메모리 확보
  • 단가 하락의 영향을 받지 않음 → 압축 ROI가 유지됨
  • 캐시 TTL·정책을 직접 설계 가능 (무제한 프리픽스 캐시)
온프렘 우선순위왜기대 효과
1. KV 캐시 최적화 (L3)
GQA/MLA 모델 선택 + FP8 KV + PagedAttention + 프리픽스 캐시		 같은 GPU로 동시 처리 요청 수를 직접 늘림. 설정 수준으로 적용 가능하며 품질 영향 거의 없음 처리량 4~8×
2. 도메인 파인튜닝
긴 시스템 프롬프트 → 모델 가중치		 온프렘 데이터를 쓸 수 있는 조직만의 특권. 프롬프트를 압축하는 게 아니라 아예 없애는 것 — 압축의 상위 호환 고정 프롬프트 제거
3. 라우팅 (자체 모델 계층)
소형 온프렘 → 대형 온프렘 → 외부 API 캐스케이드		 온프렘 GPU를 저난도 트래픽에 쓰고 고난도만 승급. 데이터 민감도 기준 라우팅도 동시 구현 가능 GPU 점유 40~70%↓
4. 토큰 압축 (L1) 위 3개를 소진한 뒤의 추가 레버. 다만 온프렘에서는 압축기 자체도 자사 GPU를 먹는다는 점을 반드시 계산에 넣어야 함 추가 2~3×
온프렘 특유의 함정 — API에서는 압축기를 어디서 돌리든 상관없지만, 온프렘에서는 압축기 추론도 같은 GPU 풀을 소비합니다. "압축으로 아낀 GPU 시간 > 압축기가 쓴 GPU 시간"이 성립하는지 반드시 실측해야 하며, 짧은 프롬프트에서는 이 부등식이 역전됩니다.

S8한 장 요약

하지 말 것

  • 압축 알고리즘 자체 개발 — 오픈소스가 이미 SOTA
  • 압축률 극대화 경쟁 — 20× 벤치마크는 자사 도메인에서 재현되지 않음
  • 캐싱 점검 없이 압축부터 도입 — 순서가 뒤바뀌면 절감이 상쇄됨
  • 압축을 단독 KPI로 설정 — 총비용이 아니라 지표만 개선됨

할 것

  • 토큰 텔레메트리부터 — 측정 없는 최적화는 추측
  • 게이트웨이에 압축을 선택 가능한 정책으로 내장
  • 도메인 골든셋 구축 — 모든 대안의 공통 인프라가 됨
  • 온프렘이면 KV 최적화·파인튜닝을 압축보다 앞에

존속성 결론

  • 압축 기술: 계속 유효 (에이전트 토큰 폭증)
  • 압축 독립 과제: 수명 중기, 플랫폼 기능으로 흡수
  • 진짜 장기 자산: 라우팅 정책 · 골든셋 · 온프렘 서빙 역량 · 파인튜닝 데이터
  • 압축은 수단이지 목표가 아님
Final Answer

Q. 토큰 압축을 길게 가져가도 되는 과제인가?

A. "토큰 압축 과제"로는 길게 가져가지 마십시오. "컨텍스트 효율화 과제"로 확장해 길게 가져가십시오. 그 안에서 압축은 캐싱이 통하지 않는 경로 전용 모듈로 15% 정도의 비중이 적절합니다. 온프렘 환경이라면 압축의 위상이 한 단계 올라가지만, 그때도 KV 최적화와 파인튜닝이 먼저입니다.

Azure 관점 요약

Azure는 "압축 알고리즘"을 제공하지 않습니다. 대신 같은 목적을 플랫폼 기능으로 해결합니다 — 보낼 필요가 없게 만들고(캐싱·상태 저장), 자동으로 줄이고(Compaction), 필요할 때만 로드(Tool Search)합니다.

특히 Responses API의 Compaction은 사실상 관리형 컨텍스트 압축 기능이며, LLMLingua 같은 OSS를 직접 붙이지 않아도 에이전트 컨텍스트 폭증 문제를 API 파라미터 하나로 처리합니다. Azure 사용자라면 OSS 압축 도입 전에 이 기능들을 먼저 소진해야 합니다.

A1Azure 기능을 4개 레이어에 매핑하면

앞선 「기술 동향」 탭의 L1~L4 프레임에 Azure 제공 기능을 얹으면 빈 칸이 어디인지가 명확해집니다.

L1 · 컨텍스트 압축
Azure: 있음 (관리형)
Responses Compaction context_management.compact_threshold Tool Search (툴 정의 지연 로드) Azure AI Search 시맨틱 랭커 (RAG 정밀도)

읽는 법 — Azure는 L4가 압도적으로 두텁고, L1은 관리형으로 일부 제공, L2는 없고, L3는 통제 불가입니다. 즉 Azure 위에서는 "L4 최대 활용 → L1 관리형 기능 → 그래도 부족하면 OSS 압축" 순서가 자연스럽습니다. L3를 직접 만지고 싶다면 Foundry가 아니라 AKS 자가 서빙으로 내려가야 합니다.

A2Responses API 네이티브 토큰 절감 기능

Chat Completions에는 없고 Responses API에만 있는 기능들입니다. 이것이 Azure가 미는 방향입니다.

◆

Compaction (컨텍스트 압축) context_management 핵심

대화·툴 호출·추론 아이템이 누적된 컨텍스트를 필수 상태만 남기고 자동 축약합니다. 앞 탭에서 설명한 "에이전트 Compaction 패턴"의 관리형 구현체입니다.

  • 수동 — /responses/compact 호출 후 반환된 compacted.output을 다음 턴 입력으로 사용
  • 서버측 자동 — context_management.compact_threshold 설정 시, 출력 토큰이 임계치를 넘으면 API가 알아서 압축 수행
  • store=false(무상태)에서도 동작하며, 결과는 암호화된 compaction 아이템으로 전달됨
  • 멀티에이전트(multi_agent.enabled=true) 사용 시 자동 활성화되며 루트/서브에이전트별로 독립 수행
◆

상태 저장 체이닝 previous_response_id

대화 이력을 매 턴 재전송하지 않고 이전 응답 ID만 넘깁니다. 클라이언트가 히스토리를 들고 다닐 필요가 없어집니다.

  • store=true가 전제. 응답은 기본 30일 보관되며 ID로 조회·삭제 가능
  • WebSocket 모드에서는 최근 응답 상태를 커넥션 로컬 메모리 캐시로 유지해 지연시간이 더 낮음(store=false 호환)
  • 주의 — 데이터 보존이 발생하므로 규제 워크로드는 보존 정책 검토 필수
◆

Tool Search (툴 정의 지연 로드) tool_search

툴이 수십 개일 때 전부 앞에 붙이지 않고, 모델이 필요할 때 검색해서 그 정의만 컨텍스트에 로드합니다. 툴 개수가 늘어도 기본 컨텍스트 비용이 평평해집니다.

  • gpt-5.4 이상 지원. 발견된 툴을 컨텍스트 뒤쪽에 주입해 앞부분 프롬프트 캐시를 깨지 않음 — 설계가 영리한 지점
  • Foundry Agent Service의 Toolbox tool search는 별개 기능 (버전 관리되는 툴박스 대상). 툴 10~15개 이상이면 권장
  • 개별 함수 단위보다 namespace · MCP 서버 단위로 defer할 때 절감폭이 큽니다. 단 tool_search_output.tools가 바뀌면 그 지점부터 캐시가 깨집니다
◆

추론 상태 제어 reasoning.context · encrypted_content

추론 모델의 reasoning 아이템을 얼마나 다음 턴으로 넘길지 제어합니다. 넘기면 품질↑·토큰↑, 안 넘기면 그 반대.

  • current_turn — 현재 턴 추론만 사용 (토큰 절약)
  • all_turns — 이전 턴 추론까지 렌더링 (연속성↑, gpt-5.6 계열만 지원 · 기본값)
  • store=false인 경우 include에 reasoning.encrypted_content를 넣어 암호화된 형태로 이어감
◆

출력 토큰 제어 reasoning_effort · verbosity · max_output_tokens

추론 모델은 출력이 비용의 대부분입니다. 앞 탭의 TokenSkip(CoT 압축)에 대응하는 공식 제어 수단이 파라미터로 제공됩니다.

  • reasoning_effort: none/minimal → low → medium → high — 단순 태스크는 낮출수록 큰 절감
  • verbosity로 답변 장황함 제어, max_output_tokens로 상한 고정
  • 주의: minimal에서는 병렬 툴 호출 미지원 등 제약이 있음

A4Compaction 실사용 — Azure판 "에이전트 컨텍스트 압축"

앞 탭 §8에서 손으로 구현하던 요약-교체 루프를, Azure는 파라미터 한 줄로 대체합니다.

① 서버측 자동 압축 (권장) python
resp = client.responses.create(
  model="gpt-5.6",
  input=messages,
  tools=tools,
  context_management={
      "compact_threshold": 120000
  },
  store=False,     # 무상태에서도 동작
)
# 임계치 초과 시 API가 자동 압축
# 응답에 암호화된 compaction 아이템 포함
에이전트 루프에 가장 적합. 별도 /compact 호출이 필요 없습니다.
② 수동 압축 (제어권 필요 시) python
compacted = client.responses.compact(
    response_id=prev.id      # 또는 items 직접 전달
)

next_resp = client.responses.create(
  model="gpt-5.6",
  input=[
     *compacted.output,      # 압축된 상태
     {"role": "user",
      "content": "영업시간도 추가해줘"}
  ],
)
압축 시점을 직접 정하거나, 압축 전후를 로깅·비교해야 할 때 사용합니다.
제약 확인 — 멀티에이전트 오케스트레이션(multi_agent.enabled=true)에서는 /responses/compact 엔드포인트를 쓸 수 없고, 서버측 자동 압축이 강제 활성화됩니다(임계치만 override 가능). 또한 이 모드에서는 reasoning.summary와 max_tool_calls가 지원되지 않습니다.

Azure 특유의 함정

  • 모델 세대별 파라미터 상이 — gpt-5.6 미만에 prompt_cache_options를 보내면 400 오류
  • 캐시 쓰기 과금 — gpt-5.6+ Standard에서는 접두부가 자주 바뀌면 오히려 비용 증가
  • 요청당 캐시 쓰기 4회 제한 — implicit 모드에서는 최신 메시지가 1슬롯 소모
  • PTU-M은 breakpoint 미지원 — 배포 형태에 따라 설계가 달라짐
  • store=true는 30일 보존 — 데이터 거버넌스 검토 필요
  • 리전 제한 — Responses API 지원 리전 확인 필수(한국은 koreacentral 지원)

KT 맥락에서의 시사점

  • 온프렘 데이터 요건이 강하면 Foundry(관리형) + AKS 자가 서빙 하이브리드가 현실적
  • Azure 구간은 캐싱·Compaction으로 충분 — 압축 R&D를 별도로 태울 이유가 약함
  • 자가 서빙 구간에서만 L3(KV) + L1(압축)이 진짜 과제가 됨
  • APIM AI Gateway를 공통 관제면으로 두면 두 구간의 토큰 지표를 한 곳에서 관리 가능
  • 즉 과제명은 "토큰 압축"보다 "토큰 관제·효율화 게이트웨이"가 적합
