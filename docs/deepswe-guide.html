② instruction.md — 에이전트가 보는 전부

ts-pattern's `match` short-circuits on the first matching pattern.
Add a new top-level function `matchEach` that evaluates ALL
registered patterns and collects every matching handler's result
into an array, returned in the order clauses were declared.

`matchEach` must expose the same builder API as `match`, including
all `.with()` overloads, `.when()`, `.returnType()`, and `.narrow()`.

`.run()` and `.exhaustive()` return an array of all matching handler
results. If nothing matched, they throw `NonExhaustiveError`.
...
Add `matchEach` as a named export from the package entry point.

IMPORTANT: Please work on this in a new branch from main and
commit everything when you are done.
힌트도, 파일 경로도, 테스트도 없습니다. 하지만 공개 API 이름·시그니처는 전부 못 박혀 있습니다. 사실상 인터페이스 계약서입니다 — 이게 나중에 테스트가 코드를 호출하는 근거가 됩니다.

import { matchEach, P } from '../src';   // ← 에이전트가 짠 코드를 import

it('should collect all matching handler results', () => {
  const results = matchEach({ role: 'admin', level: 7, active: true })
    .with({ role: 'admin' },          () => 'is-admin')
    .with({ level: P.number.gte(5) }, () => 'is-senior')

컨테이너 내부 구조

파일이 들어오는 경로가 3가지입니다. 이 구분이 핵심입니다.

컨테이너 내부 /
├── app/ 🔥 이미지에 구워짐 (baked)
│ └ ts-pattern 레포 전체. base commit 상태. 미래 히스토리 삭제됨
│
├── logs/ 🔗 호스트와 bind mount
│ ├── agent/ ← trial_dir/agent/ (에이전트 로그·트라젝토리)
│ ├── verifier/ ← trial_dir/verifier/ (reward.json, ctrf.json)
│ └── artifacts/ ← trial_dir/artifacts/ (model.patch) ★
│
├── tests/ 📤 나중에 업로드 (copy)
│ └ 에이전트가 끝난 뒤 채점 컨테이너에만 올라감. ①에는 존재 자체가 없음
│
└── solution/ 📤 oracle 에이전트일 때만
    └ 일반 실행에서는 절대 안 올라감
🔥 baked — 이미지 빌드 시 포함. 항상 존재 🔗 mount — 호스트 폴더와 실시간 연결 📤 copy — 실행 중 특정 시점에 업로드
이것이 커닝이 불가능한 이유. /tests와 /solution은 마운트가 아니라 업로드입니다. 작업 컨테이너 ①이 살아있는 동안 그 경로는 존재하지 않습니다. 에이전트가 ls /tests를 해도 No such file or directory가 나옵니다.

마운트 상세 — 딱 3개

Pier가 컨테이너에 거는 bind mount는 이게 전부입니다.

컨테이너 경로호스트 경로용도
/logs/agent/ jobs/<job>/<trial>/agent/ 에이전트 로그, 트라젝토리(trajectory.json) — pier view가 읽는 파일
/logs/verifier/ jobs/<job>/<trial>/verifier/ 채점 결과: reward.json, ctrf.json, run.log, test-stdout.txt
/logs/artifacts/ jobs/<job>/<trial>/artifacts/ ★ 제출 답안 model.patch — 컨테이너 ①→②로 건너가는 통로
왜 마운트인가? 컨테이너는 끝나면 사라집니다. 마운트해두면 결과물이 호스트 디스크에 그대로 남습니다. 그래서 실행이 끝난 뒤에도 cat jobs/*/*/verifier/reward.json으로 점수를 볼 수 있습니다.
실행 후 Pier가 chown으로 소유권을 호스트 유저에게 되돌려줍니다 — 컨테이너가 root로 쓴 파일을 사람이 못 읽는 문제 방지.

제출 답안이 컨테이너를 건너가는 법

① 작업 컨테이너 안에서 (collect 훅)
git diff --binary <base> HEAD > /logs/artifacts/model.patch
                                  ↓ 마운트라서 즉시 호스트에 반영
② 호스트
jobs/<job>/<trial>/artifacts/model.patch
                                  ↓ 새 컨테이너에 같은 경로로 마운트
③ 채점 컨테이너 안에서 (grader.py)
git apply /logs/artifacts/model.patch

두 컨테이너는 서로를 모릅니다. 네트워크로 통신하지 않고, 오직 호스트의 파일 하나를 통해서만 연결됩니다.

네트워크 — 기본은 완전 차단

Pier는 docker-compose 오버레이를 겹쳐서 구성합니다.

기본 (인터넷 불필요한 에이전트) 
# docker-compose-no-network.yaml
services:
  main:
    network_mode: none   # 랜선 뽑기

DNS도 안 됨. GitHub에서 정답을 fetch하는 게 물리적으로 불가능.

예외 (LLM API가 필요할 때)

Claude Code처럼 컨테이너 안에서 도는 에이전트는 API 호출용 통로가 필요합니다. Pier는 egress 프록시 + 도메인 allowlist를 붙입니다. 

# 허용된 도메인만 통과
allowlist = ["api.anthropic.com",
             "my-model.example.com"]

⚠️ base URL을 config에 적어야 Pier가 자동 등록합니다. 코드에 하드코딩하면 차단됨.

이게 Pier가 Harbor를 포크한 이유입니다. Harbor는 allow_internet = false면 전부 막아버려서 컨테이너 내부 CLI 에이전트가 LLM을 호출조차 못 했습니다. Pier는 "태스크 환경은 격리하되, 에이전트에게 필요한 통로만 열어주는" 방식으로 바꿨습니다.

레포 전체는 수백 MB, diff는 20KB

깨끗한 재현

원본 + diff만 있으면 어디서든 동일 재현. 캐시·임시파일 오염이 안 딸려옴

검토 가능

사람이 "정확히 뭘 바꿨나" 한눈에 확인

⚠️ 커밋 안 하면 무조건 0점. git diff <base> HEAD는 커밋된 것만 봅니다. 파일을 아무리 잘 고쳐놨어도 커밋을 안 하면 HEAD가 시작 커밋 그대로라 diff가 빈 문자열이 되고 → 테스트 전부 실패 → reward: 0. 실전에서 가장 흔한 사고입니다.

그래서 이 diff로 뭘 하나 — 읽는 게 아니라 재현합니다

가장 많이 오해하는 지점입니다. diff는 평가 대상이 아니라 재현 재료입니다.

❌ 이렇게 하지 않습니다
  • diff를 읽고 "잘 짰네" 판단
  • diff를 모범답안과 비교
  • diff를 LLM에게 읽혀서 채점
  • 줄 수·파일 수를 세서 점수화

정적 분석이나 유사도 비교는 전혀 없습니다.

✅ 실제로 하는 일
  • 새 컨테이너에 diff를 적용
  • 에이전트가 만든 코드 상태로 복원
  • 숨겨진 테스트를 실제로 실행
  • 통과/실패 개수로 채점

코드를 진짜로 돌려봅니다.

재현 과정 5단계

1

새 컨테이너 기동 에이전트 흔적 0

같은 이미지로 완전히 새로 띄웁니다. /app은 base commit 원본 상태.

2

제출 답안 적용 → 코드 복원

# grader.py
reset_paths(patch_paths(read_patch(model_patch)), base)   # 먼저 원본으로
rc = git("apply", "--whitespace=nowarn", model_patch).returncode

if rc != 0:
    cmd_grade(["--apply-failed"])   # ← 여기서 끝. 테스트 실행 안 함
    sys.exit(0)

이 시점에 /app은 에이전트가 작업을 끝낸 그 상태가 됩니다.

3

숨겨진 테스트 강제 투입 test.patch

reset_paths(patch_paths(read_patch(test_patch)), "HEAD")  # 조작분 되돌리고
git("apply", test_patch)                              # 원본 테스트 적용

에이전트가 테스트를 고쳐놨더라도 여기서 전부 덮어씌워집니다.

4

진짜로 실행 평범한 유닛테스트

npx jest tests/helpers.test.ts     → P2P 결과
npx jest tests/match-each.test.ts  → F2P 결과

여기서 코드가 실제로 동작합니다. 정적 분석이 아니라 실행입니다.

5

결과 대조 → 점수

실행 리포트의 테스트 ID를 config.json의 F2P/P2P 목록과 맞춰봅니다.

왜 굳이 새 컨테이너에서 재현하나?
에이전트가 3시간 작업한 컨테이너에는 설치한 패키지, npm 캐시, 수정한 전역 설정 (jest.config.js, ~/.npmrc), 몽키패칭, 켜둔 백그라운드 프로세스가 남아 있습니다. 그 상태로 테스트하면 "내 컴퓨터에선 되는데요" 문제가 그대로 발생합니다. task.toml의 environment_mode = "separate"가 이를 강제합니다.
유일한 예외 — 실행 없이 결정되는 경우.
2단계에서 패치 적용이 실패하면 테스트를 돌려보지도 않고 즉시 reward 0입니다. 깨진 diff, 충돌하는 diff, 빈 diff(커밋 누락)가 여기 해당합니다. reward.json에 "apply_failed": 1이 찍힙니다.
한 줄 요약 — diff는 "판단 대상"이 아니라 "재현 재료"입니다. 새 컨테이너에서 코드를 복원한 뒤 실제로 테스트를 실행한 결과로 채점합니다.

6 정답은 하나가 아니다

문자열 비교를 하지 않습니다. 테스트를 통과하는 모든 코드가 정답입니다.

❌  내 패치 == 정답 패치 ?            ← 이렇게 안 함
✅  내 패치 적용 → 테스트 91개 통과 ?  ← 이렇게 함
제출파일 구성결과
레퍼런스match-each.ts + 4개 파일 리팩터링 (+582 −43줄)reward 1
에이전트 A파일 2개에 전부 몰아넣음, 리팩터링 안 함reward 1
에이전트 B파일 9개로 잘게 쪼갬, 내부 함수 이름 전부 다름reward 1
에이전트 C런타임은 맞는데 타입 레벨 테스트 2개 실패reward 0

왜 가능한가 — 공개 API만 고정, 내부는 자유

🚪 고정 (명세가 정함)
  • 함수·클래스 이름 → matchEach
  • 메서드 → .with() .run()
  • 반환 타입 → 배열
  • 에러 타입 → NonExhaustiveError
  • import 경로 → 패키지 엔트리포인트
🔓 자유 (완전 무관)
  • 파일 개수 / 이름 / 위치
  • 내부 헬퍼 함수 이름
  • 클래스 vs 클로저
  • 알고리즘 · 자료구조
  • 주석 · 코드 스타일

테스트는 import { matchEach } from '../src' 문 하나만 두드립니다. 그 안에서 뭘 만들든 테스트가 직접 호출할 일이 없습니다. JSON.parse()를 쓸 때 V8 내부 구현을 모르는 것과 같은 원리(캡슐화)입니다.

단, 이름을 어기면 즉사. matchEach 대신 matchAll로 만들면 → import 실패 → 스위트 컴파일 실패 → 리포트에 테스트가 하나도 안 잡힘 → "리포트에 없는 F2P = 실패" 규칙 적용 → 0점.

원본에서도 통과하던 테스트. 기존 걸 안 부쉈는가를 검사합니다.

12 왜 이 벤치마크가 특별한가

🆕 원본성 (contamination 회피)

기존 GitHub 이슈 재탕이 아니라 새로 창작한 과제. 모델이 학습 데이터에서 정답을 외우고 있을 가능성이 낮습니다.

⏳ Long-horizon

단일 파일 버그 수정이 아니라 아키텍처를 관통하는 기능 추가. 레퍼런스 정답이 5~11개 파일, 수백 줄입니다.

🎯 동작 기반 채점

코드 유사도가 아닌 observable behavior만 봅니다. 구현 방식이 달라도 인정.

🔒 재현성

도커 이미지·base commit·자원·타임아웃이 데이터에 고정. 누가 언제 돌려도 같은 조건.

왜 mini-swe-agent를 기준선으로 쓰나

스캐폴드가 얇을수록 점수 ≈ 모델 실력에 가까워집니다. Claude Code나 OpenCode처럼 자체 프롬프트·도구·컨텍스트 관리가 두꺼운 에이전트를 쓰면 "모델이 잘한 건지 스캐폴드가 잘한 건지" 구분이 안 됩니다. mini-swe-agent는 bash 도구 하나, 선형 히스토리, 상태 없는 실행이라 약 100줄짜리 에이전트입니다.

3에이전트 코드 작성 (더미 버전)

BaseAgent를 상속해 4개 메서드만 구현하면 됩니다: name(), version(), setup(), run().

sample-agent/sample_agent/agent.py
from pier.agents.base import BaseAgent
from pier.environments.base import BaseEnvironment
from pier.models.agent.context import AgentContext


class SampleAgent(BaseAgent):
    """가장 단순한 에이전트: 아직 LLM 없이 동작만 확인."""

    SUPPORTS_ATIF = False      # 트라젝토리 포맷 미지원
    SUPPORTS_WINDOWS = False

    def __init__(self, logs_dir, model_name=None, extra_env=None, **kwargs):
        super().__init__(logs_dir=logs_dir, model_name=model_name, **kwargs)
        self._extra_env = extra_env or {}
        # config yaml 의 kwargs 가 여기로 들어옴
        self._max_steps = kwargs.get("max_steps", 30)

    # --- 필수 4개 -------------------------------------------------

    @staticmethod
    def name() -> str:
        return "sample-agent"

    def version(self) -> str:
        return "0.1.0"

    async def setup(self, environment: BaseEnvironment) -> None:
        """에이전트 실행 전 준비. 지금은 할 일 없음."""
        return

    async def run(self, instruction: str, environment: BaseEnvironment,
                  context: AgentContext) -> None:
        self.logger.info(f"instruction 길이: {len(instruction)}자")

        # ① 환경 탐색 — 진짜 에이전트라면 여기서 LLM 루프를 돈다
        ls = await environment.exec(command="ls /app")
        self.logger.info(f"/app 내용: {ls.stdout}")

        # ② 코드 수정 (지금은 흔적만 남김)
        await environment.exec(
            command="echo '// sample-agent was here' >> /app/README.md"
        )

        # ③ ★★★ 커밋 — 안 하면 무조건 0점 ★★★
        await environment.exec(
            command=(
                "cd /app && git checkout -b sample-agent && git add -A && "
                'git -c user.name=agent -c user.email=a@b '
                'commit -q --no-verify -m "sample-agent work" || true'
            )
        )

        # ④ 지표 기록 (리포트·비용 집계용)
        context.n_agent_steps = 3
        context.cost_usd = 0.0
        context.metadata = {"note": "dummy run"}
③번이 이 튜토리얼에서 가장 중요합니다. Pier도 도커도 커밋을 대신 해주지 않습니다. git diff <base> HEAD는 커밋된 것만 보기 때문에 커밋이 없으면 빈 패치 → 무조건 reward 0입니다.

7LLM 붙이기 (진짜 에이전트로)

이제 더미를 실제 LLM 루프로 교체합니다. bash 하나만 주는 최소 구조입니다 (mini-swe-agent와 같은 철학).

sample-agent/sample_agent/agent.py — run() 교체
import re, os
from openai import AsyncOpenAI

SYSTEM = """You are a coding agent working in /app.
Reply with EXACTLY ONE bash command inside a ```bash block.
When the task is complete, reply with: TASK_DONE"""

async def run(self, instruction, environment, context):
    client = AsyncOpenAI(api_key=self._extra_env["OPENAI_API_KEY"],
                         base_url=self._extra_env.get("OPENAI_BASE_URL"))
    msgs = [{"role": "system", "content": SYSTEM},
            {"role": "user",   "content": instruction}]

    in_tok = out_tok = 0
    for step in range(self._max_steps):
        r = await client.chat.completions.create(
            model=self._parsed_model_name, messages=msgs)
        reply = r.choices[0].message.content
        in_tok  += r.usage.prompt_tokens
        out_tok += r.usage.completion_tokens
        msgs.append({"role": "assistant", "content": reply})

        if "TASK_DONE" in reply:
            break

        m = re.search(r"```bash\n(.*?)```", reply, re.S)
        if not m:
            msgs.append({"role": "user",
                         "content": "Reply with one ```bash block."})
            continue

        # 액션 실행 → 결과를 그대로 다음 턴 입력으로 (선형 히스토리)
        res = await environment.exec(command=m.group(1), timeout_sec=120)
        obs = (res.stdout or "") + (res.stderr or "")
        msgs.append({"role": "user", "content": f"exit={res.return_code}\n{obs[:4000]}"})

    # ★ 안전망: LLM이 커밋을 깜빡해도 반드시 커밋
    await environment.exec(command=(
        "cd /app && git add -A && "
        'git -c user.name=agent -c user.email=a@b '
        'commit -q --no-verify -m "agent work" || true'))

    context.n_input_tokens  = in_tok
    context.n_output_tokens = out_tok
    context.n_agent_steps   = step + 1

네트워크 허용 선언

DeepSWE 태스크는 network_mode = "no-network"입니다. 컨테이너 안에서 LLM API를 호출하려면 도메인을 열어달라고 선언해야 합니다. 

from pier.models.agent.network import NetworkAllowlist

    def network_allowlist(self) -> NetworkAllowlist:
        return NetworkAllowlist(domains=["api.openai.com"])
주의. localhost나 127.0.0.1은 컨테이너 안에서 자기 자신이라 호스트의 로컬 모델에 접근할 수 없습니다. 자체 모델을 쓰려면 컨테이너에서 도달 가능한 호스트명(공인 도메인, 터널링 URL 등)을 쓰고 그 도메인을 allowlist에 넣으세요.

에이전트를 컨테이너 안에 설치해야 한다면

CLI 바이너리가 필요한 경우 install_spec()으로 이미지 빌드 단계에 설치할 수 있습니다.

from pier.models.agent.install import AgentInstallSpec, InstallStep

    def install_spec(self) -> AgentInstallSpec:
        return AgentInstallSpec(
            agent_name=self.name(), version=self.version(),
            steps=[InstallStep(run="pip install openai", user="root")],
            verification_command="python -c 'import openai'",
        )

※ 위 LLM 루프는 호스트(Pier 프로세스)에서 API를 호출하고 컨테이너엔 exec만 보내는 구조라, 사실 install_spec도 network_allowlist도 필요 없습니다. 둘 다 필요한 건 Claude Code처럼 에이전트 자체가 컨테이너 안에서 도는 경우입니다.

✓실패 체크리스트

reward가 계속 0이라면 위에서부터 순서대로 확인하세요.

  • oracle이 1.0인가? → 아니면 환경 문제 (도커·디스크·이미지)
  • model.patch가 비어 있는가? → 커밋 누락. 가장 흔한 원인
  • apply_failed: 1인가? → 패치 충돌. base commit 외 파일을 건드렸는지 확인
  • f2p_passed가 0인가? → 공개 API 이름이 명세와 다를 가능성. 컴파일 실패 여부를 run.log에서 확인
  • p2p가 깨졌는가? → 기존 코드를 망가뜨림. 리팩터링 범위를 줄일 것
  • LLM 호출이 안 되는가? → no-network 차단. allowlist 또는 호스트 호출 구조 확인
  • 타임아웃인가? → max_steps를 줄이거나 프롬프트를 개선

🧠 내 모델만 테스트하기

에이전트는 검증된 mini-swe-agent를 그대로 쓰고 모델만 갈아끼웁니다. 코드는 한 줄도 작성하지 않습니다. 설정 파일만 쓰면 됩니다.

왜 mini-swe-agent를 쓰나? 스캐폴드가 얇을수록 점수 ≈ 모델 실력에 가까워집니다. 두꺼운 에이전트를 쓰면 "모델이 잘한 건지 스캐폴드가 잘한 건지" 구분이 안 됩니다. DeepSWE 리더보드도 전부 mini-swe-agent 기준입니다.

3⚠️ 네트워크 함정 — 여기서 대부분 막힙니다

DeepSWE 태스크는 task.toml에 이렇게 박혀 있습니다.

[agent]
network_mode = "no-network"   # 컨테이너 외부 통신 전면 차단

그런데 mini-swe-agent는 컨테이너 안에서 실행됩니다(installed agent). 즉 LLM API 호출도 컨테이너 안에서 나갑니다. 그냥 두면 차단되죠.

Pier는 이를 위해 egress 프록시 + 도메인 allowlist를 자동 구성합니다. Pier 소스의 network_allowlist()가 다음 위치에서 URL을 긁어옵니다: 

# pier/agents/installed/mini_swe_agent.py
for key in ("OPENAI_BASE_URL", "OPENAI_API_BASE",
            "ANTHROPIC_BASE_URL", "GEMINI_API_BASE",
            "OPENROUTER_API_BASE"):
    if value := self._get_env(key):
        urls.append(value)          # ← 여기서 자동 등록

if self._config_yaml:
    urls.extend(collect_url_values(parsed))   # config_yaml 안의 URL도
✅ 되는 것
  • env에 명시한 base URL
    → 자동으로 allowlist 등록
  • 공인 도메인 / 사내 DNS로 잡히는 호스트
  • kwargs.config_yaml 안의 URL
❌ 안 되는 것
  • localhost / 127.0.0.1
    → 컨테이너 안에선 자기 자신
  • 코드에 하드코딩한 URL
    → Pier가 못 읽어서 차단
  • 사설 IP (컨테이너에서 라우팅 불가 시)
로컬 vLLM을 쓰고 싶다면? 컨테이너에서 도달 가능한 주소로 노출해야 합니다. ① ngrok/cloudflared 등으로 터널링 → 공인 도메인 사용, ② 또는 같은 네트워크의 다른 머신에 서빙하고 그 호스트명 사용. 어느 쪽이든 그 URL을 env에 반드시 적어야 allowlist에 등록됩니다.

OpenCode 내장 레지스트리에 없는 모델을 쓰려면 provider 설정을 주입해야 합니다. Pier는 kwargs.opencode_config를 opencode.json에 deep-merge합니다.

⚠️ 가장 많이 틀리는 부분. OpenCode는 base URL을 provider 루트가 아니라 options.baseURL에서 읽습니다. 위치가 틀리면 조용히 무시됩니다. 
provider:

5네트워크 allowlist — 자동 처리

DeepSWE는 no-network인데 OpenCode는 컨테이너 안에서 API를 호출합니다. Pier는 provider 설정에서 URL을 긁어 자동으로 허용합니다. 

# pier/agents/installed/opencode.py
def network_allowlist(self) -> NetworkAllowlist:
    provider, _ = self.model_name.split("/", 1)
    config = self._build_runtime_config(include_mcp=False)
    provider_config = (config.get("provider") or {}).get(provider) or {}
    urls = collect_url_values(provider_config)      # ← 설정 속 URL 수집
    return allowlist_from_urls(
        urls,
        default_domains=self._DEFAULT_PROVIDER_DOMAINS.get(provider, []))

provider별 기본 허용 도메인:

anthropic  → api.anthropic.com        openai     → api.openai.com
google     → .googleapis.com          openrouter → openrouter.ai
groq       → api.groq.com             mistral    → api.mistral.ai
deepseek   → api.deepseek.com         xai        → api.x.ai
커스텀 엔드포인트라면 env.OPENAI_BASE_URL 또는 opencode_config.provider.*.options.baseURL에 반드시 명시하세요. 적어두기만 하면 allowlist 등록은 자동입니다.
※ localhost는 컨테이너 안에서 자기 자신이라 불가

9주의사항 체크리스트

  • provider/model 형식 필수 — 아니면 즉시 ValueError
  • baseURL 위치 — options.baseURL이어야 함. 루트에 두면 무시
  • 설치 시간 — nvm + npm 설치가 이미지 빌드에 포함돼 첫 실행이 오래 걸림
  • 타임아웃 — 도구가 많아 턴이 길어짐. override_timeout_sec 상향 검토
  • 비용 — mini-swe-agent보다 컨텍스트·턴 수가 많아 토큰 비용이 큼
  • 커밋 확인 — model.patch가 비어있지 않은지 반드시 검증
  • 에러 이벤트 — OpenCode가 error 이벤트를 뱉으면 Pier가 NonZeroAgentExitCodeError로 실패 처리

🗜 Headroom 압축 레이어 평가하기

Headroom은 LLM 트래픽을 중간에서 압축하는 로컬 프록시입니다. DeepSWE로 "토큰을 N% 줄였을 때 정확도가 얼마나 떨어지는가"를 측정합니다.

핵심 아이디어. deep-swe도 Pier도 전혀 건드리지 않습니다. 모델 URL만 Headroom 프록시로 바꿔치기하면 됩니다. 에이전트 입장에선 그냥 평범한 OpenAI 호환 엔드포인트로 보입니다.

1구조 — 프록시를 중간에 끼운다

// 원래
에이전트 ──────────────────────────▶ 모델 API

// Headroom 적용

2실행 옵션 해설

실제 DeepSWE v1 평가에 쓰인 옵션 조합입니다.

headroom proxy \
  --mode token \
  --code-aware \
  --target-ratio 0.8 \
  --intercept-tool-results \
  --no-cache \
  --no-ccr \
  --backend openai \
  --openai-api-url $MODEL_URL
옵션의미
--mode token 압축 우선 모드. 이전 턴까지 다시 써서(rewrite) 최대한 줄입니다. (반대는 cache — 이전 턴을 얼려서 provider 캐시 적중률을 높이는 모드)
--code-aware AST 기반 코드 압축 활성화. 코딩 벤치마크라 필수. 기본값은 꺼짐이며 pip install headroom-ai[code] 필요
--target-ratio 0.8 텍스트를 원본의 80%만 유지. 낮출수록 공격적 (0.4면 40%만 유지). 미지정 시 Kompress가 알아서 보수적으로 판단
--intercept-tool-results 툴 출력도 압축 (ast-grep Read outliner 등). 에이전트는 cat·grep 출력이 컨텍스트의 대부분이라 효과가 큽니다. ⚠️ HEADROOM_ROLLOUT_CHANNEL=canary 필요
--no-cache 시맨틱 캐시 끔. 캐시가 켜져 있으면 "압축 덕분"인지 "캐시 덕분"인지 구분 불가. 벤치마크에선 반드시 꺼야 합니다
--no-ccr 가역 압축(CCR) 끔. CCR은 원문을 로컬에 보관하고 모델이 headroom_retrieve 툴로 되찾는 기능인데, mini-swe-agent는 bash 외 툴이 없어서 그 툴을 호출할 수 없습니다. 켜두면 모델에게 dangling pointer만 남습니다 → 반드시 꺼야 함
--backend openai
--openai-api-url		 업스트림을 OpenAI 호환 엔드포인트로 지정. $MODEL_URL이 실제 모델 주소
--no-ccr와 --no-cache가 벤치마크의 생명입니다.
• 캐시가 켜지면 토큰 절감이 압축 때문인지 캐시 때문인지 섞여버립니다.
• CCR이 켜지면 압축된 자리에 "필요하면 headroom_retrieve로 되찾아라"는 마커가 남는데, bash만 쓰는 에이전트는 그 툴이 없어 정보가 그냥 사라진 것과 같아집니다.

3설치 및 프록시 기동

# code-aware 를 쓰려면 [code] extra 필수 (tree-sitter)
pip install 'headroom-ai[code]'

# tool_result 인터셉터는 canary 채널에서만 동작
export HEADROOM_ROLLOUT_CHANNEL=canary
export MODEL_URL=https://api.openai.com

headroom proxy --port 8787 --host 0.0.0.0 \
  --mode token --code-aware --target-ratio 0.8 \
  --intercept-tool-results --no-cache --no-ccr \
  --backend openai --openai-api-url $MODEL_URL

기동되면 OpenAI 호환 엔드포인트가 열립니다.

http://<호스트>:8787/v1      # /v1/chat/completions, /v1/responses ...

4⚠️ 가장 중요 — 컨테이너에서 프록시에 닿게 하기

mini-swe-agent는 컨테이너 안에서 돌고, 태스크는 no-network입니다. 프록시가 호스트의 localhost:8787에 있으면 컨테이너에서 접근 불가합니다.

❌ 이렇게 하면 실패 
OPENAI_BASE_URL:
  http://localhost:8787/v1

컨테이너 안의 localhost는 컨테이너 자신. 연결 거부됩니다.

✅ 해결책
  • 터널링 — cloudflared/ngrok으로 공인 도메인 부여 (가장 확실)
  • 별도 호스트 — 다른 머신·사내 서버에 프록시를 띄우고 그 호스트명 사용
  • Modal 사용 시 — 어차피 클라우드라 공인 주소 필수
URL만 env에 적으면 allowlist는 자동입니다. Pier의 network_allowlist()가 OPENAI_BASE_URL 값을 읽어 egress 프록시 허용 목록에 넣어줍니다. 코드 수정 불필요.

5A/B 실험 설계

변수는 딱 하나(압축 여부)여야 합니다. 태스크·시드·모델·에이전트를 모두 동일하게 맞춥니다.

headroom-eval.yaml
job_name: headroom-ab
n_concurrent_trials: 4
n_attempts: 3              # LLM 확률성 → 3회 평균으로 노이즈 감소

datasets:
  - path: ./deep-swe/tasks
    n_tasks: 20
    sample_seed: 0          // ★ 두 조건이 같은 20개를 받음

environment:
  type: docker

agents:
  # ── A: 기준선 (압축 없음)
  - name: mini-swe-agent
    model_name: openai/gpt-5.5
    env:
      OPENAI_API_KEY: ${OPENAI_API_KEY}
      OPENAI_BASE_URL: https://api.openai.com/v1

  # ── B: Headroom 경유 (압축)
  - name: mini-swe-agent
    model_name: openai/gpt-5.5        # 모델 동일
    env:
      OPENAI_API_KEY: ${OPENAI_API_KEY}
      OPENAI_BASE_URL: https://my-headroom.trycloudflare.com/v1
pier run --config headroom-eval.yaml
n_attempts: 3을 권장합니다. LLM은 확률적이라 1회 실행으로는 "압축 때문에 떨어진 건지 그냥 운이 나빴는지" 구분되지 않습니다. 태스크 20개 × 3회 = 60 trial × 2 조건 = 120 trial이므로 Modal 사용을 권장합니다.

7실험 신뢰도를 지키는 규칙

  • --no-cache 필수 — 캐시 적중이 섞이면 압축 효과를 분리할 수 없음
  • --no-ccr 필수 — bash만 쓰는 에이전트는 headroom_retrieve를 호출할 수 없음
  • sample_seed 고정 — 두 조건이 반드시 같은 태스크를 받아야 함
  • 모델·에이전트 동일 — 바꾸는 건 OPENAI_BASE_URL 하나뿐
  • n_attempts ≥ 3 — LLM 확률성 노이즈 완화
  • 프록시 안정성 확인 — 프록시가 죽으면 API 오류가 "정확도 하락"으로 잘못 집계됨
  • 타임아웃 여유 — 압축 처리로 지연이 늘면 override_timeout_sec 상향 검토
가장 흔한 오염 원인. 프록시 장애(타임아웃·5xx)로 에이전트가 중간에 멈추면 reward 0이 되는데, 이건 압축 품질과 무관합니다. pier view로 트라젝토리를 열어 API 오류로 끝난 trial은 제외하고 집계하세요.
