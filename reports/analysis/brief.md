# LLM 프롬프트 압축 성능 영향 평가 — 요약

Terminal Bench 2.1 · DeepSWE · LLMLingua-2 · 최종 추론 gpt-5.4 · 2026-09-04

## 요약

**압축 강도를 높일수록 정확도가 단조 하락했습니다.** 기준 조건 63.6% 에서 가장 강한 압축(`rate 0.5`)의 27.3% 까지 -36.4%p 떨어졌으며, 같은 조건의 토큰 절감은 -51.5% 였습니다.

측정 변동(±18.2%p)을 넘어선 하락은 `rate 0.5` 이하에서 나타났습니다. 그보다 완만한 구간은 변동 안에 있으며, 그중 가장 강한 `rate 0.7` 는 토큰을 -28.1% 줄이면서 정확도 하락이 -13.6%p 였습니다. **다만 이 값 역시 변동 범위 안이라 이득을 확정할 수 없습니다.**

컨텍스트가 27배 큰 DeepSWE 에서는 토큰이 실제로 감소했으나(최대 -47.8%), 이슈 해결 진척도(f2p)가 56.3% 에서 38.9% 이하로 떨어졌습니다. 호출 한도를 초과해 과제를 끝내지 못한 trial 이 4건 발생했고 **전부 압축 조건**이었습니다. trial 소요 시간은 최대 18배로 늘었습니다.

**종합하면, 큰 폭의 토큰 절감은 정확도 저하를 동반했고, 정확도를 지키는 완만한 구간의 이득은 측정 변동과 구분되지 않았습니다.** 현 시점에서 프롬프트 전면 적용은 권고하지 않으며, 아래 선택적 적용을 검토하고 표본을 늘려 재측정할 것을 제안합니다.


## 1. 무엇을 쟀나

공식 하네스(`pier` · Docker 격리)로 에이전트를 실제 실행하고 저장소 테스트로 채점했습니다. 압축은 에이전트와 모델 사이 프록시에서 적용됩니다.

```
[에이전트]
     ↓
[압축 프록시]  llmlingua-2-xlm-roberta-large-meetingbank
               → 남길 토큰만 분류 (로컬 CPU · 생성 아님)
     ↓
[추론]         gpt-5.4 (Azure AI Foundry)
     ↓
[테스트로 채점]
```

> **모델이 두 개 쓰입니다.** 압축은 `microsoft/llmlingua-2-xlm-roberta-large-meetingbank` 가 각 토큰을 남길지만 판정하는 방식이라 텍스트를 새로 만들지 않고, 외부 API 도 부르지 않습니다. **최종 추론은 전 조건 동일하게 gpt-5.4** 를 호출하며, 보고서의 pass@1·토큰 지표는 모두 이 호출 기준입니다.

> 세로축은 **위 표의 값 ÷ 기준 조건 값**입니다. `pass@1` 와 `입력 토큰` 두 열만 그렸습니다. 예를 들어 `llmlingua2-r0.9` 줄은 pass@1 59.1% ÷ 63.6% = **0.93×**, 입력 토큰 29,826 ÷ 38,605 = **0.77×** 로 찍힙니다. 기준 조건은 두 선 모두 1.00× 입니다. 0.50× 는 기준의 절반이라는 뜻이며, `pass@1` 값이 50% 라는 뜻이 **아닙니다**. 토큰은 낮을수록 좋고 `pass@1` 는 낮을수록 나쁘므로, **두 선이 함께 내려가면 절감의 대가로 품질을 내주고 있다는 뜻입니다.**

> 태스크 단위로 보면 44개 대응쌍 중 **14개에서 입력 토큰이 오히려 증가**했습니다(최대 `sqlite-db-truncate` +229%). 그중 11개는 에이전트 호출 횟수도 늘었습니다 — 압축으로 손상된 컨텍스트가 재탐색을 유발해 절감분을 상쇄한 것으로 보입니다.

## 4. 두 벤치마크 비교

두 벤치마크는 같은 압축기·조건·최종 모델을 썼고 **부하 규모만 다릅니다.** DeepSWE 의 누적 입력이 Terminal Bench 의 **27배**입니다.

**표 4.** 벤치마크별 요약

| 벤치마크               | 기준 입력 토큰  | 지표     | 기준값   | 최대 하락   | 최대 토큰 절감 | 품질 유지 한계   |
|------------------- |----------:|------- |------:|--------:|---------:|----------- |
| Terminal Bench 2.1 | 38,605    | pass@1 | 63.6% | -36.4%p | -51.5%   | `rate 0.9` |
| DeepSWE            | 1,042,174 | pass@1 | 20.0% | -20.0%p | -47.8%   | **없음**     |

> ‘품질 유지 한계’ 는 기준 조건 대비 지표 하락이 5%p 이내였던 가장 강한 압축 조건입니다. ‘없음’ 은 측정 범위의 모든 압축 조건에서 그보다 큰 하락이 관측되었다는 뜻입니다.

압축 연산 지연은 Terminal Bench 에서 호출당 중앙 1.1초였으나 DeepSWE 에서는 **52.1초**로 커졌습니다. LLMLingua-2 는 입력 전체를 토큰 단위로 분류하므로 연산량이 컨텍스트 길이에 비례합니다.

> **압축이 가장 필요한 대규모 컨텍스트에서 압축 오버헤드도 가장 큽니다.** 에이전트는 한 과제에 수십 번 호출하므로 이 지연이 누적됩니다.


## 5. 판단 근거의 한계

조건당 태스크 11종을 1회씩만 시도했습니다. 태스크 1건의 성패가 pass@1 을 9.1%p 움직입니다. 동일 조건을 반복한 압축 없이 반복 측정에서 실제 변동은 pass@1 ±18.2%p, 입력 토큰 ±20.3% 였으며, 이는 본 측정에서 관측된 변화와 같은 크기입니다.

> 따라서 **효과의 방향(압축할수록 나빠짐)은 판별 가능하나, 크기는 확정할 수 없습니다.** 크기를 확정하려면 태스크 수와 시도 횟수를 함께 늘려야 합니다.

> 본 결과는 LLMLingua-2 · gpt-5.4 · mini-swe-agent 조합, 그리고 프롬프트 전체에 일괄 적용하는 방식에 한정됩니다. 메시지 유형별 선택 적용은 평가하지 않았습니다.


## 6. 권고

압축기 자체는 정상 동작했습니다. 산문형 입력은 절반으로 압축해도 핵심 정보가 남습니다. 문제는 **명령 실행 출력의 식별자가 손상**된다는 점이며, 에이전트는 그 식별자로 후속 명령을 구성하므로 이것이 성능 저하의 직접 경로입니다.

**표 5.** 후속 검토 방향

| 방향                                       | 근거                                    |
|----------------------------------------- |-------------------------------------- |
| 명령 출력에 규칙 기반 축약 적용 (로그 중복 제거·스택 트레이스 축약) | 식별자를 보존하면서 가장 크게 증가하는 영역을 줄입니다.       |
| 산문형 입력(과제 설명·문서)에만 선택 적용                 | 해당 유형은 압축률 대비 정보 손실이 작습니다.            |
| `keep_last` 확대 후 정확도 회복 지점 탐색            | 직전 컨텍스트 보존 범위의 영향이 통제되지 않았습니다.        |
| 단순 절단(truncation) 압축 없이 반복 측정과 비교        | 압축기 도입 비용을 정당화하려면 단순 기법 대비 우위가 필요합니다. |
| 태스크 수·시도 횟수 확대 후 재측정                     | 현재 표본으로는 효과 크기를 확정할 수 없습니다.           |
