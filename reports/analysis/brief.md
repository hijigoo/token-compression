# LLM 프롬프트 압축 성능 영향 평가 — 요약

Terminal Bench 2.1 · DeepSWE · LLMLingua-2 · 최종 추론 gpt-5.4 · 2026-09-04

## 요약

⚠️ **측정이 아직 진행 중입니다.** DeepSWE(조건별 1~2/3 trial) — 조건별 표본 수가 서로 다르므로 아래 수치는 잠정값이며, 롤아웃 완료 후 갱신됩니다. 확정 결과로 인용하지 마십시오.

**결론: 현 시점에서 코딩 에이전트 프롬프트에 대한 전면 적용은 권고하지 않습니다.** 압축 강도를 높일수록 정확도가 하락했고(최대 -37.5%p), 정확도를 유지한 구간에서는 토큰이 줄지 않았습니다.

정확도를 지킨 가장 강한 압축은 `rate 0.9` 였으나 입력 토큰은 +24.1% 로 절감 효과가 없었고, 실제로 토큰이 크게 준 `llmlingua2-r0.5`(-48.2%)는 정확도가 -37.5%p 하락했습니다. **측정 범위에서 정확도와 비용이 함께 개선되는 지점은 없었습니다.**

단, 동일 조건 반복 측정에서 pass@1 이 ±25.0%p 변동했습니다. 하락 경향은 일관되나 **개별 수치의 크기는 현재 표본으로 확정할 수 없습니다.**


## 1. 무엇을 쟀나

공식 하네스(`pier` · Docker 격리)로 에이전트를 실제 실행하고 저장소 테스트로 채점했습니다. 압축은 에이전트와 모델 사이 프록시에서 적용되며, **최종 추론은 전 조건 동일하게 gpt-5.4**(Azure)를 호출합니다.

```
[에이전트] → [압축 프록시: 프롬프트 일부 삭제] → [gpt-5.4]
                                                    ↓
                                        [테스트로 채점]
```

## 4. 두 벤치마크 비교

두 벤치마크는 같은 압축기·조건·최종 모델을 썼고 **부하 규모만 다릅니다.** DeepSWE 의 누적 입력이 Terminal Bench 의 **37배**입니다.

**표 4.** 벤치마크별 요약

| 벤치마크               | 기준 입력 토큰  | 기준 pass@1 | 최대 정확도 하락 | 최대 토큰 절감 | 정확도 유지 한계  |
|------------------- |----------:|----------:|----------:|---------:|----------- |
| Terminal Bench 2.1 | 31,156    | 62.5%     | -37.5%p   | -48.2%   | `rate 0.9` |
| DeepSWE            | 1,137,919 | 0.0%      | +0.0%p    | -57.4%   | `rate 0.5` |

> ‘정확도 유지 한계’ 는 pass@1 하락이 5%p 이내였던 가장 강한 압축 조건입니다. ‘없음’ 은 모든 압축 조건에서 그보다 큰 하락이 관측되었다는 뜻입니다.

압축 연산 지연은 Terminal Bench 에서 호출당 중앙 1.7초였으나 DeepSWE 에서는 **45.8초**로 커졌습니다. LLMLingua-2 는 입력 전체를 토큰 단위로 분류하므로 연산량이 컨텍스트 길이에 비례합니다.

> **압축이 가장 필요한 대규모 컨텍스트에서 압축 오버헤드도 가장 큽니다.** 에이전트는 한 과제에 수십 번 호출하므로 이 지연이 누적됩니다.


## 5. 판단 근거의 한계

조건당 태스크 8종을 1회씩만 시도했습니다. 태스크 1건의 성패가 pass@1 을 12.5%p 움직입니다. 동일 조건을 반복한 대조 측정에서 실제 변동은 pass@1 ±25.0%p, 입력 토큰 ±45.5% 였으며, 이는 본 측정에서 관측된 변화와 같은 크기입니다.

> 따라서 **효과의 방향(압축할수록 나빠짐)은 판별 가능하나, 크기는 확정할 수 없습니다.** 크기를 확정하려면 태스크 수와 시도 횟수를 함께 늘려야 합니다.

> 본 결과는 LLMLingua-2 · gpt-5.4 · mini-swe-agent 조합, 그리고 프롬프트 전체에 일괄 적용하는 방식에 한정됩니다. 메시지 유형별 선택 적용은 평가하지 않았습니다.


## 6. 권고

압축기 자체는 정상 동작했습니다. 산문형 입력은 절반으로 압축해도 핵심 정보가 남습니다. 문제는 **명령 실행 출력의 식별자가 손상**된다는 점이며, 에이전트는 그 식별자로 후속 명령을 구성하므로 이것이 성능 저하의 직접 경로입니다.

**표 5.** 후속 검토 방향

| 방향                                       | 근거                                    |
|----------------------------------------- |-------------------------------------- |
| 명령 출력에 규칙 기반 축약 적용 (로그 중복 제거·스택 트레이스 축약) | 식별자를 보존하면서 가장 크게 증가하는 영역을 줄입니다.       |
| 산문형 입력(과제 설명·문서)에만 선택 적용                 | 해당 유형은 압축률 대비 정보 손실이 작습니다.            |
| `keep_last` 확대 후 정확도 회복 지점 탐색            | 직전 컨텍스트 보존 범위의 영향이 통제되지 않았습니다.        |
| 단순 절단(truncation) 대조군과 비교                | 압축기 도입 비용을 정당화하려면 단순 기법 대비 우위가 필요합니다. |
| 태스크 수·시도 횟수 확대 후 재측정                     | 현재 표본으로는 효과 크기를 확정할 수 없습니다.           |
